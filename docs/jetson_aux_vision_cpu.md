# carrot-nav-pv5: CPU 차선·BSD와 Wi-Fi

`ShareData`의 기존 차선 종류 분류와 `OnnxBsdEnabled`의 시각 BSD ONNX 계산을
Jetson CPU로 옮긴다. 두 설정은 기본 OFF와 기존 온로드 준비 조건을 유지한다.
차량 BSD, 분류 클래스·임계값·ROI·평활화, 차선변경 제어 조건과 N16 주행 모델은
유지한다. 이 변경은 별도의 전방 차량 거리/위치 검출기를 추가하지 않는다.

## 데이터와 실행

- 콤마는 기존 회색조 차선 입력과 마스크/레터박스 BSD 입력을 만든다. 입력은
  각각 uint8 416×416, 352×352×3이다. JPEG 재압축 없이 같은 픽셀을 보낸다.
- 영상과 결과는 **직접 Wi-Fi AP의 TCP 7717**만 사용한다. 콤마의 `wljetson0`
  게이트웨이 주소, 같은 전용 /24의 Jetson 주소, 실제 출력 장치와 중간 게이트웨이가
  없는 경로를 매 요청 확인한다. 휴대폰 핫스팟/공유기·USB/NCM/이더넷 우회는 금지한다.
- USB에서는 세션 시작 때 지원 기능과 임시 키만 협상한다. 기존 HUD와 주행 모델의
  공식 USB 경로는 유지한다. 보조 영상은 주행 모델 USB 프레임에 넣지 않는다.
- 기존 인증 교환에서 용도가 분리된 키를 만들고 AES-GCM, 순서 번호, 요청 ID와
  ONNX SHA-256으로 상대·결과를 확인한다. 키를 명령행/상태/로그에 기록하지 않는다.
- 양쪽에 별도 보조 작업을 둔다. Jetson은 OpenCV DNN CPU 백엔드/타깃, OpenCL OFF,
  OpenCV/BLAS 스레드 1개, 일반 스케줄링 nice10, 허용 CPU 중 앞의 최대 2개를 쓴다.
  콤마 릴레이와 영상 전처리는 일반 우선순위 nice19로 실행한다. 주행 GPU 계산이나
  제어 스레드의 우선순위를 바꾸지 않는다.

## 부하와 유효성

- 초기 차선 간격은 500ms, BSD는 **좌우 합산** 500ms다. 양쪽이 설정되면 각 방향은
  번갈아 처리하므로 최대 1Hz다. 더 짧은 기존 저장값은 실행할 때만 500ms로 제한하고
  저장값을 덮어쓰지 않는다. 반복/후속 감지를 더 빠르게 실행하지 않는다.
- 동시 계산은 1개, 각 연결 대기열은 1개, 요청은 최대 380,000바이트, 응답은 최대
  4,096바이트다. 콤마의 전체 RPC 마감은 750ms다. Jetson은 이전 계산 시간의
  1/4만큼 다음 계산을 쉬어 단일 CPU 스레드의 지속 점유를 제한한다. 이는 공유
  메모리·전력 간섭까지 격리하는 cgroup 보장이나 20Hz 동작 보장은 아니다.
- 원시 입력만 계산하면 최대 약 8.72Mbit/s이며 인증·전송·재시도 비용은 별도다.
  실제 속도를 측정한 수치가 아니다. CPU와 Wi-Fi가 느리면 요청률은 더 낮아진다.
- 결과 시각은 콤마의 원래 카메라 촬영 시각이다. 미리 250ms 이상 지난 영상과
  미래 시각은 보내지 않는다. 원격 차선은 촬영 후 1초, BSD는 기존 1.5초 이내에서만
  사용한다. Jetson과 콤마의 서로 다른 시계를 비교하거나 완료 시각으로 나이를
  초기화하지 않는다. 단절/지연/해시 불일치는 unknown이며 로컬 ONNX fallback은 없다.
  응답 없는 연결은 5초 유휴 제한으로 닫아 재연결이 막히지 않게 한다.
- BSD OFF는 기존 세대 번호/동시 갱신 보호를 유지하고 콤마 결과를 즉시 무효화한다.
  원격 모델 해제를 요청하고, 호스트에서도 3초간 쓰이지 않은 모델을 해제한다.
  프로세스/할당기 캐시 때문에 RSS가 즉시 같은 크기로 줄어든다는 뜻은 아니다.
  차량이 제공한 BSD를 원격의 false 결과로 지우지 않는다.
- 이 이식은 기존 차선변경 제어 정책을 대체하지 않는다. 원격 응답 없음은 안전한
  차선이라는 판정이 아니며 운전자가 주변과 기존 차량 경고를 확인해야 한다.

## 설치와 확인

콤마와 대응 Jetson 런타임을 함께 업데이트해야 한다. 기존 SHA USB 수신기를
등록한 장치는 콤마 브랜치 업데이트 후 Jetson 정상 재부팅으로 새 묶음을 받는다.
P단/정지 조건, SHA/크기/ABI 검사, 공식 NAS 서명 복귀 경로는 유지한다.
처음 받는 파일은 콤마의 인터넷 또는 검증된 캐시가 필요하다.

이 브랜치는 [공개 대응 패키지](https://github.com/tjdgus200/openpilot/releases/tag/jetson-pv5-aux-wifi-20261021-c56183fd)를
선택한다. 소스 `c56183fd`, 81,667,195바이트이며 SHA-256은
`40688dad244c63683b232de766a13e4812b06b19ff6ecae8a19597759161a849`다.
공개 HTTPS 재다운로드로 검증했다. 공식 N16 파일은 변경하지 않았고 묶음에
주행 모델을 다시 포함하지 않는다. 콤마만 업데이트하면 이전 Jetson이 CPU 기능을
자동으로 갖는 것이 아니며, 정상 부팅 수신기가 이 대응 묶음을 설치해야 한다.

호스트 묶음에는 기존 두 ONNX와 CPU 소스를 포함한다. OpenCV가 필요하며 새 설치의
`requirements-jetson.txt`는 NumPy 1.26과 호환되는 CPU wheel 4.10.0.84를 지정한다.
이미 실행 가능한 OpenCV가 있으면 설치 중 강제로 교체하지 않는다. 설치 전 별도
CPU 자식 프로세스에서 두 모델을 로드/실행하고 메모리를 반환한 후 기존 주행 GPU
검사를 실행한다. 의존성/실행 검사가 실패하면 기존 릴리스를 유지한다.

캐럿 웹의 기존 상세 상태는 `processor=jetson_cpu_wifi`, `transport=wifi`를 보고하고
실제 최근 원격 응답이 있어야 모델 준비 완료로 표시한다. 오래된 호스트는 지원
기능을 광고하지 않으므로 영상 전송과 콤마의 대체 ONNX를 시작하지 않는다.

PC 검사는 실제 두 ONNX의 로컬/원격 입력 결과, 인증·재전송/변조 거부, 입력 크기와
순서, 잘못된 모델/상대/응답, 차량 BSD 보존, 촬영 시각, 원래 BSD ON/OFF 동시성,
ROI·스냅샷·NV12 전처리를 포함한다. 네이티브 IPC는 명시적인 import용 대체 구현과
테스트 소켓을 사용하며 실제 CAN/카메라/차량 제어나 GPU 성능 검증으로 세지 않는다.
이번 브랜치의 온로드·크루즈·유효 맵과 동시 실행한 실기기 20Hz 측정은 별도다.

## 실패 진단과 표시

차선 `lane.diagnostic`, BSD `model.diagnostic`와 웹 상단의 두 진단 행은 고정된
`code`/`stage`/설명을 제공한다. 실제 요청·성공·실패·진행 중 횟수도 구분한다.
기존 차선 `inference.count`는 실패 결과까지 포함하는 시도 횟수이므로
`countKind=attempts`로 명시한다. 시간 값과 요청 FPS만으로 추론 성공을 판단하지 않는다.

| 분류 | 대표 코드 | 확인한 범위 |
| --- | --- | --- |
| 구버전/설치 | `runtime_outdated`, `runtime_incomplete` | 기능 미광고와 기능 사용 불가를 구분. 미광고가 아닌 false만으로 구버전이라고 단정하지 않음 |
| 의존성/모델 | `dependency_missing`, `model_missing`, `model_load_failed`, `model_hash_mismatch` | 지원되는 새 호스트가 확인한 OpenCV·모델 로드·해시 문제 |
| 세션/릴레이 | `session_setup_timeout`, `session_setup_rejected`, `relay_start_failed`, `relay_unavailable` | USB의 초기 세션 협상과 콤마의 별도 릴레이 시작 상태 |
| Wi-Fi | `wifi_local_unavailable`, `wifi_peer_unavailable`, `wifi_route_unavailable`, `wifi_connect_failed` | 로컬 주소, 신선한 상대 주소, 실제 WLAN 경로, 접속 실패를 구분 |
| 인증 | `authentication_failed`, `authentication_timeout` | HMAC/AEAD 거부와 인증 대기 시간 초과를 구분. 시간 초과만으로 키 불일치라고 단정하지 않음 |
| 추론 | `inference_failed`, `inference_invalid_result` | 인증된 요청의 호스트 계산 실패와 결과 형식/유한값 오류 |
| 미확정 | `response_timeout`, `remote_closed` | 응답 시간 초과/연결 종료만으로 무선·CPU 계산 중 어느 원인인지 단정할 수 없음 |

BSD 원격 실패는 카메라 단절로 기록하지 않으며 VisionIPC 연결을 유지한다.
영상 나이와 카메라 오류는 별도로 표시하고, 실패한 BSD 결과는 무효화한다.
차량 고유 BSD와 기존 unknown/유효시간 정책은 유지한다. 실패 재시도도 기존
좌우 합산 500ms 제한을 따르며 빠른 반복/추가 추론을 만들지 않는다.

호스트의 상세 오류는 USB HELLO의 `carrot_aux_cpu_diagnostics_v1`으로 구분한다.
인증 및 AEAD 복호화, 요청 ID/해시 검사를 통과한 오류 응답만 받는다. 오류 응답은
`valid=false`이며 차선 없음/차 없음 결과로 바꾸지 않는다. 모든 상태는 허용한
고정 코드만 전달한다. OpenCV 원문·입력 영상·네트워크 비밀·키·환경변수는 상태에
포함하지 않는다. 구형 CPU 호스트에는 상세 진단 미지원이 표시되며, 그 호스트가
단순히 연결을 닫은 경우 추론 오류라고 추측하지 않는다.

새 상세 진단의 완전한 사용에는 대응 Jetson 패키지도 업데이트해야 한다.
콤마 Git Pull/정상 재부팅과 Jetson 정상 재부팅을 사용하는 기존 경로다.
단순 표시 개선으로 Wi-Fi 안정성·주행 인식·20Hz가 검증됐다는 뜻은 아니다.

[진단 소스 CI](https://github.com/tjdgus200/openpilot/actions/runs/39565949638)는
루트 수신/복구 103개, 넓은 통합 검사 1,212개(선택적 61개 건너뜀), 내비/장면
119개, 실제 격리 파일시스템 11개와 격리 Wi-Fi 패킷 11개 및 Windows 디스크
선택 검사를 통과했다. 중복을 포함하므로 고유 검사 수로 합산하지 않는다.
PC에서 실제 로컬 소켓과 인증/암호화 소켓의 오류 전달·변조 거부, 실제 두 ONNX,
카메라 연결 유지·BSD OFF 동시성·전처리를 검사했다. Linux의 Node 없는 검사는
건너뛰되 Windows Node에서 실제 웹 스크립트 문법과 KO/EN/ZH 진단 렌더 함수를
별도로 실행했다. 최종 설치 묶음은 안전하게 격리 추출한 뒤 두 CPU 모델과 HUD
진입점을 실행하고 공개 HTTPS 전체 재다운로드의 크기/SHA도 확인했다.

## 듀얼 Wi-Fi 코드 확인

`wifi_direct_netlink.py`는 `wlan0`와 같은 PHY에 별도 `wljetson0` AP를 만들기 전에
드라이버의 동시 station/AP 조합 지원을 확인한다. `wifi_direct.py`는 기존 `wlan0`
프로필을 바꾸지 않는다. 사용자 후속 요청에 따라 **온로드 부팅에서도 AP를 자동 생성/
복구**하며, 활성 AP는 온로드에도 유지한다. 따라서 휴대폰을 콤마의 AP로 쓰는 구조가 아니라
`wlan0 → 휴대폰`과 `wljetson0 AP → Jetson`을 함께 사용하는 구조를 지원한다.
한 PHY의 가상 인터페이스이므로 독립된 두 무선 장치가 있다는 뜻은 아니다.

사용자 추가 요청으로 이 브랜치는 **직접 AP만 허용**한다. `wifi_publisher.py`는
소유한 활성 AP 한 개만 읽어 `wifi_policy=direct_only`와 실제 AP 서브넷을 개인 USB
채널로 전달한다. 휴대폰과 기타 저장 프로필의 암호를 읽거나 Jetson에 보내지 않는다.
AP가 없으면 프로필은 빈 값이며 공용 WLAN으로 바꾸지 않는다. 이미 활성화된 AP의
SSID·암호·클라이언트 식별자는 휴대폰 접속/해제로 바뀌지 않는다. 기존 독립 네트워크
수신기는 새 AP 연결 확인 뒤 이전 콤마가 관리하던 핫스팟 프로필을 제거한다.
관리자가 직접 저장한 프로필은 지우지 않지만 보조 데이터 경로에는 사용할 수 없다.

Jetson의 새 수신 작업은 USB로 전달된 프로필로 계산한 NetworkManager UUID와
현재 장치가 일치하고 그 주소가 전용 서브넷인 경우에만 수신 소켓을 연다. 상대도
그 AP의 콤마 게이트웨이 주소여야 하며 기존 세션 인증을 유지한다. 휴대폰 주소가
생기거나 사라져도 이 수신 주소 목록을 바꾸지 않는다. Wi-Fi HUD를 협상하는 구형
화면 경로에도 같은 제한을 적용한다. 현재 공식 USB HUD와 주행 모델·업데이트·초기
Wi-Fi 정보 전달의 USB 경로를 Wi-Fi로 옮기는 변경은 아니다.

휴대폰은 콤마 `wlan0`의 인터넷 업링크로만 쓴다. Jetson이 인터넷이 필요하면 기존
전용 AP의 NAT를 거쳐 콤마 업링크를 사용한다. 핫스팟이 꺼져도 AP를 내리지 않으며
인터넷 공유 설정 실패는 로컬 AP를 종료하지 않는다. AP 절전 해제도 유지한다.
보호 OS/독립 복구 서비스를 교체하거나 새 관리자 권한을 추가하지 않는다.

`diagnostic.wifiPath`와 웹 진단 행은 최근 검증된 응답 경로만 `direct_ap`로 표시한다.
이전 버전이 보고한 `shared_wifi`의 표시 호환성만 남긴다. 3초 이상 관측이 없으면
`unknown`이며, 무응답 동안 예전
경로를 현재 연결 보장처럼 표시하지 않는다. AP 활성화와 DHCP가 끝나기 전,
드라이버/채널 제약 또는 RF 문제로 직접 연결이 준비되지 않을 수 있다. 코드 검사와
PC 회귀에서는 직접 AP만 선택·공용 WLAN/다른 서브넷/경유 라우트 거부,
핫스팟 해제·복귀 시 프로필/수신 주소 유지와 기존 네트워크 수신기 호환성을 검사한다.
격리 Linux veth 시험은 실제 라우트와 패킷으로 업링크 해제 중 직접 경로를 검사한다.
물리적 장치의 동시 연결·채널 변경·주행 중 회복을 측정한 결과는 아니다. 단일 PHY의
드라이버가 AP+STA를 동시에 유지하지 못하거나 RF가 끊기면 소프트웨어가 무선을
보장할 수 없다. 이때 핫스팟으로 우회하지 않고 오류/unknown으로 표시한다.

선택한 PC 회귀는 220개 통과, 선택적 2개는 별도 환경 조건으로 생략했다.
웹 진단은 Windows Node에서 별도로 실행했고, 격리 Linux의 실제 네트워크 패킷
검사 11개도 통과했다. 이 숫자는 중복을 포함하며 실제 RF/장치 설치 결과가 아니다.

## 핫스팟 없는 온로드 부팅

전용 AP 생성/재연결에서 `IsOffroad` 제한을 제거했다. 콤마와 Jetson의 USB 제어
연결이 준비되면 기존 개인 채널로 전용 AP 정보가 전달되고 Jetson의 독립 네트워크
수신기가 자동 연결한다. 휴대폰 핫스팟을 켜거나 온로드/기어 상태를 조작할 필요는 없다.
AP가 준비되기 전에도 USB 업데이트 제어 패킷은 계속 전달한다. 준비 전 프로필 확인은
5초 간격이며, 정상 AP 확인 뒤에는 30초 간격으로 줄인다. 주 루프는 2초 단위이므로
실제 확인은 해당 간격 이후 처음 순회에서 진행한다. AP/NM/DHCP와 Jetson의 기존
재시도 간격이 필요하므로 부팅 순간의 0초 연결을 약속하는 기능은 아니다.

AP와 프로필 전달 작업은 별도 프로세스에서 SCHED_OTHER/nice19, 코어 0–3으로
실행한다. AP 시작/복구의 NetworkManager 대기나 실패가 주행 모델 프레임 경로를
기다리게 하지 않는다. 실패한 활성화는 30초 뒤 재시도하고, 활성 AP는 5초 간격으로
확인하며 다시 만들지 않는다. 채널은 기존 스캔 캐시만 읽고 핫스팟이 없으면 기존
5GHz 채널 36 선택을 사용한다. 강제 스캔·휴대폰 프로필 재접속·전체 Wi-Fi 라디오
토글·USB 재설정·주행 작업의 코어/우선순위 변경은 추가하지 않는다. 별도 NAT 보정은
계속 오프로드에서만 실행하며, 보정 실패 때문에 로컬 AP를 종료하지 않는다.

PC 검사에서 온로드/핫스팟 없음 AP 활성화, 준비 지연 후 자동 설정 전달, 30초 실패
재시도와 정상 AP 유지, 별도 실행·우선순위·소유 자원 한정을 확인한다. 모의 NM과
Linux 격리 패킷은 실제 무선 펌웨어의 지연이나 CPU/GPU 부하 측정이 아니다.
모델·CAN/크루즈·결과 유효성·공식 직렬 USB는 유지하지만 공유 PHY/커널 자원 때문에
실제 주행에 영향이 전혀 없다는 보장은 할 수 없으며 장치 측정이 필요하다.

이 시작 조건 변경은 콤마 Git Pull/정상 재부팅으로 적용한다. 기존 대응 호스트
`61878ca0`와 USB 프로필/인증 형식은 같으므로 이 변경 때문에 Jetson 패키지를
다시 설치할 필요는 없다. 아직 대응 패키지가 없는 장치는 앞 절의 설치가 먼저 필요하다.

## 설치 검사의 낮은 CPU 우선순위 유지

부팅 업데이터는 nice19로 실행되고, `runuser -u jetlink`로 실행하는 후보 검사와
그 자식 CPU ONNX 검사에도 이 값이 전달된다. 기존 `vision_cpu.py --check-models`는
일반 계정에서 nice10을 요청해 CPU 우선순위를 높이려 했으므로, 기본 Linux 권한에서
모델 로딩 전에 `PermissionError`로 종료될 수 있었다. 콤마에는 후보 활성화 실패
요약만 전달되므로 이 오류가 USB 인증 실패로 보일 수 있지만 별도 문제다.

CPU 보조 작업은 요청값과 상속값 중 더 낮은 우선순위(더 큰 nice 값)를 선택한다.
일반 시작의 송신 nice19/수신 nice10은 같고, 이미 nice19인 설치 검사는 nice19를
유지한다. SCHED_OTHER 전환, 두 CPU 코어 한정, 한 계산 스레드와 CUDA 비활성화는
유지한다. 관리자 권한·스케줄링 능력을 추가하거나 예외를 무시하지 않는다.

기존 공개 패키지의 함수는 Linux 비관리자 자식에서 nice0 시작은 통과했지만
nice19 시작은 권한 오류로 재현됐다. 수정 함수는 nice19를 유지하며 통과한다.
당시 패키지는 실제 두 CPU ONNX 검사, HUD 진입점과 GPU 후보 검사를 필수로 실행했다.
아래 후속 변경에서는 설치 시 CPU ONNX 실행 검사만 제거했다.
PC 재현은 사용자의 Jetson 내부 오류 기록이나 주행 안정성 검증을 대신하지 않는다.

Jetson에서 실행되는 파일이므로 수정된 호스트 패키지가 필요하다. 콤마의 이
브랜치를 Git Pull/재부팅하고 USB를 유지한 채 Jetson도 정상 재부팅하는 기존
설치 경로를 사용한다. 기존 수신 허용 정책·키·SHA 검사·P단/정차 승인과 이전
릴리스 보존은 유지하며, 실행 중인 주행 엔진을 교체하지 않는다.

수정된 대응 호스트의 소스는 `4e3acd5e05f5be51c109265d8973f8c96de6e599`이며,
공개 패키지는 [설치 검사 우선순위 수정 Release](https://github.com/tjdgus200/openpilot/releases/tag/jetson-pv5-install-priority-20261021-4e3acd5e)에 있다.
`usb_host_sha256_release.json`은 이 패키지의 81,665,759바이트와 SHA-256
`cec20f4f924c4dab2f789936860d448322933c853bb330a18e326155f4144440`을 고정한다.
주행 모델의 SHA/크기와 ARM64·L4T·TensorRT 조건은 기존 선택과 같다.
이전 runtime-port 수신기의 명세 검사도 통과한다. 패키지·체크섬·메타데이터·USB
명세를 인증 없는 공개 HTTPS 주소에서 모두 다시 내려받아 로컬 파일과 비교했다.

공개 아카이브에서 추출한 실제 차선·BSD 두 ONNX를 비관리자 nice19 자식으로
검사했고, 종료 때 nice19/SCHED_OTHER 유지와 HUD의 실제 `--help` 진입점도 확인했다.
관련 PC 회귀 164개가 통과했고 선택 검사 1개는 생략했다. 소스 커밋의
[GitHub Actions](https://github.com/tjdgus200/openpilot/actions/runs/39594324792)도 통과했다.
이 배포 준비 검사는 실제 Jetson의 설치 완료·GPU 실행·무선 지연·주행 검증을
의미하지 않는다. 장치는 기존 후보 실행 검사를 통과해야 새 버전으로 전환한다.

## 재부팅 조사 중 설치 시 CPU 모델 실행 검사 제거

사용자가 검증 도중 BOOT 시간이 초기화되는 전체 재부팅을 보고했다. 콤마 상태에는
기존 Jetson 소스 `0320f54d`가 응답한 뒤 검증 상태에서 USB 연결이 사라지는 것이
관측됐다. 커널·전원 기록은 확보하지 못했으므로 CPU 검사 때문에 재부팅됐다고
확정하지 않는다. 사용자 요청으로 활성화 전 `vision_cpu.py --check-models` 호출을
제거하며, 이 진입점은 기존 `0320f54d`의 검사 코드와 같아진다.

패키지 SHA/길이·모델 계약·런타임·수신 허용 정책 검사, 실제 HUD 시작 검사와
GPU 엔진 로드/준비·3회 유한 출력 검사는 유지한다. 실패 시 이전 릴리스 복구도
그대로다. 차선/BSD 모델 파일·Wi-Fi 전송·CPU 작업자·결과 유효성 처리는 유지한다.
보조 ONNX가 실행 시 실패하면 기존 오류/무효 결과 처리를 사용한다. 따라서 설치
성공 자체가 보조 CPU 모델 실행 성공을 보증하지는 않는다. 수동 `--check-models`
진입점은 남기되 부팅 활성화 검사에서 자동 실행하지 않는다.

PC 검사는 실제 후보 검사 진입점에 GPU 대역을 연결해 HUD 실패·엔진 로드 실패·
모델 계약 불일치·비유한/빈 출력이 계속 설치를 거부하는지 확인한다. 이는 실제
Jetson의 GPU 실행이나 재부팅 해결을 입증하는 검사가 아니다. 새 대응 패키지가
필요하며 콤마 Git Pull/재부팅과 USB 연결을 유지한 Jetson 정상 재부팅으로 전달한다.

사용자가 새 공개 업로드를 승인한 대응 패키지는
[CPU 설치 검사 제거 Release](https://github.com/tjdgus200/openpilot/releases/tag/jetson-pv5-no-cpu-probe-20261021-bfe0cab1)다.
소스 `bfe0cab1c322eb8636117cc90c5e25b1153c84da`, 크기 81,666,735바이트,
SHA-256 `7f37058718cb75533c39daa6651da1f997c41779bf716ed0693a8477852204f0`을
USB 배포 명세에 고정한다. 패키지·체크섬·메타데이터·USB 명세를 모두 공개 HTTPS에서
인증 없이 다시 내려받아 로컬 크기와 SHA를 대조했다. 내보낸 후보 검사 파일이
기존 `0320f54d`와 같고 차선/BSD 작업자·모델 핀·인증/복구 파일이 이전 선택과
같은지도 확인했다. 실제 내보낸 HUD 진입점 검사와
[소스 CI](https://github.com/tjdgus200/openpilot/actions/runs/39609059542)는 통과했다.
실장치 설치나 재부팅 해결을 확인한 결과는 아니다.

## 실제 서버 시작 경로 검사 보완 (2026-10-22)

차량에서 분리한 장치에서 `bfe0cab1`은 설치·TensorRT 엔진 로드·유한 출력 3회
검사를 통과했다. 그러나 실제 systemd 서버는 `openpilot` 모듈을 찾지 못해
재시작했다. 서버가 릴리스 루트를 Python 검색 경로에 추가하지 않았고, 기존
검사는 이미 루트를 추가한 부모 프로세스에서 서버를 import해 이를 놓쳤다.

서버 진입점이 자신의 릴리스 루트를 직접 추가하도록 수정한다. 후보 검사는
`tools/jetlink`를 작업 디렉터리로 쓰는 새 Python 프로세스에서 `PYTHONPATH`를
제외하고 서버를 import한다. 부모 검사의 검색 경로가 실제 서비스의 누락을
가리지 않도록 한다. 이 단계는 모듈 로딩 검사이며 보조 CPU 모델을 실행하지
않는다. 기존 HUD 진입점·GPU 모델 계약·엔진 준비·3회 유한 출력·복구는 유지한다.

임시 서비스 실행 경로 보완으로 새 런타임의 USB `ready`와 보조 CPU 기능 식별은
확인했다. 정식 대응 패키지 설치 후 임시 보완을 제거해야 한다. 이 결과는 과거
전체 장치 재부팅의 원인 확정이나 주행 성능·안전 검증을 뜻하지 않는다.

## Jetson Wi-Fi 절전 해제 유지 (2026-10-22)

이후 `f865b16d` 대응 패키지의 실제 USB 설치와 GPU 후보 검사가 통과했다.
임시 Python 경로 설정이 없는 상태에서 서버·HUD 서비스가 실행됐고, 콤마
재부팅 후에도 USB가 자동으로 복귀했다. 120초 관찰 두 구간에서 각각 120회
모두 USB `ready`였으며 서비스 재시작은 0회였다. 이 배포 선택은 유지한다.

같은 탁상 환경에서 콤마의 두 무선 인터페이스는 절전이 꺼져 있었으나 Jetson의
station은 켜져 있었다. 2초마다 1회, 1초 응답 제한의 120초 직접 경로 ping에서
60회 중 33회 응답했고, 응답한 패킷의 평균/최대는 64.77/254ms였다. 연결을
다시 시작하지 않고 Jetson 절전만 끈 다음 동일 조건에서는 57/60회 응답,
평균/최대 2.45/15.4ms였다. 신호는 약 -39dBm이었고 별도로 재연결 기록도
있었다. 시간대가 다른 짧은 비교이므로 절전이 모든 손실의 원인이라고 단정하지
않는다. 응답하지 않은 세 패킷은 평균 지연에 포함되지 않는다.

새 보호 이미지의 초기 설정·USB 가져오기 프로필은 `powersave=2`를 명시한다. 이는
[NetworkManager의 절전 해제 값](https://www.networkmanager.dev/docs/api/1.30/settings-802-11-wireless.html)이다.
기존 보호 이미지의 가져오기 코드는 USB 런타임과 독립돼 있어, 이 프로필 변경만
배포하면 이전 장치의 부팅 후 재활성화를 막을 수 없다. 따라서 새 런타임의
실제 서버 시작 시 `carrot-jetlink-wifi-power` 작업자를 별도로 예약한다.
기존 `image_first_boot.py`는 오프라인 복구 패키지의 SHA 고정 대상이므로 원본을
유지한다. 그 초기 설정을 사용하는 장치도 런타임 작업자가 보완한다.

작업자는 SCHED_OTHER/nice19, CPU0-1에서 5초마다 nl80211 상태를 읽고, 켜져
있는 station의 절전만 끈다. 정상 상태에는 SET을 반복하지 않는다. 연결 해제,
재검색, 라디오·경로 변경, NetworkManager 재시작, USB 재바인딩은 하지 않는다.
드라이버 오류 시 30초 간격으로 재시도하며, 보조 작업 시작·응답을 주행 모델
서버가 기다리지 않는다. systemd는 CAP_NET_ADMIN과 NETLINK/UNIX 소켓만 허용하고
시스템 파일을 읽기 전용으로 제한한다. 상태는 `/run/carrot-jetlink-wifi-power/status.json`에
인터페이스 이름·절전 값·고정 상태 코드만 기록하며 무선 비밀번호나 세션 키는
읽거나 기록하지 않는다. `/run` 작업자는 새 부팅에서 다시 예약된다.

이 변경은 소스 푸시이며, 현재 USB 배포 명세는 이미 검증한 `f865b16d` 패키지를
계속 선택한다. 새 작업자는 새 대응 Jetson 패키지에 포함해 설치해야 작동한다.
새 작업자의 실제 보호 이미지 부팅·재연결 유지·CPU 사용량은 아직 측정하지
않았으며, PC 회귀 통과를 실장치 또는 주행 안전·20Hz 검증으로 해석하지 않는다.

사용자가 이후 공개 배포·USB 설치·재부팅 확인을 승인한 대응 패키지는
[Wi-Fi 절전 유지 Release](https://github.com/tjdgus200/openpilot/releases/tag/jetson-pv5-wifi-power-20261022-595c509b)다.
소스 `595c509bc45161425812b872d74c7180d60a6ef5`, 크기 81,669,749바이트,
SHA-256 `d284bcdb7c24da3f38a9c102a809aebe93a38ab5415eb70c1f70118bab5c39b0`을
새 USB 명세에 고정한다. 패키지·체크섬·메타데이터·USB 명세를 공개 HTTPS에서
다시 내려받아 모두 검증했다. 원래 GPU 모델과 ABI, 설치 검사·복구 정책은 같다.
설치 직전 기존 `f865b16d` 장치의 실제 절전 값이 다시 켜져 있음을 확인했다.
새 작업자의 설치·부팅 검증 결과는 이 배포 준비 사실과 구분해야 한다.

## 서버 시작 전 절전 정책과 재접속 중복 방지 (2026-10-22)

위 `595c509b` 패키지는 이후 실제 USB 설치·GPU 후보 검사를 통과했다. Jetson과
콤마를 각각 정상 재부팅한 뒤 직접 AP 재연결과 절전 꺼짐을 확인했다. 120초에
Jetson 커널 조회 25/25회가 꺼짐, USB 상태 120/120회가 `ready`였다. 절전 유지
작업은 CPU 한 코어 기준 약 0.017%, 메모리 6.1MiB를 사용했다. 다만 초기 부팅
22.58초에는 아직 절전이 켜져 있었고 모델 서버 이후 해제돼, 초기 정책을 보완한다.

새 `wifi_boot.py`는 모델 서버가 아닌 독립 USB 부팅 검사기에서 별도 작업을
예약한다. 주행 모델·USB 검사 루프는 NetworkManager 명령이나 연결 준비를
기다리지 않는다. 예약 작업은 SCHED_OTHER/nice19, CPU0-1, idle I/O,
35초 시작 제한을 사용한다. 최초 런타임 설치 시에도 별도 작업으로 DATA의
안정된 업데이트 도구를 갱신하며, 기존 부팅 승인 마커는 그대로 보존한다.
파일·디렉터리 fsync만 사용하고 이 마이그레이션은 전체 `sync()`를 호출하지 않는다.

부팅 작업은 `/run/NetworkManager/conf.d`에 Wi-Fi 기본 절전 해제 값 2를 넣고
`nmcli general reload conf`로 설정만 다시 읽는다. 이는 연결·DNS 재시작과 다른
[공식 명령](https://www.networkmanager.dev/docs/api/latest/nmcli.html)이다.
기존 보호 이미지의 독립 가져오기 작업은 `/run/systemd/system` 덮어쓰기로
DATA의 검증된 안정 도구를 사용한다. 그 가져오기 작업만 한 번 다시 시작한다.
NetworkManager, 라디오, 모델·HUD·USB 서비스나 읽기 전용 APP 원본을 다시
시작하거나 변경하지 않는다. 같은 부팅의 USB 검사기 재시작은 정상 가져오기
작업을 또 재시작하지 않는다. DATA 복구 실패 시 원래의 불변 복구 도구가 남는다.

기존 `carrot-usb-*.nmconnection` station의 절전 필드만 2로 바꾸고 기존 개인
설정 저장 경로로 보존한다. 비밀번호와 나머지 키파일 바이트는 유지하고 관리자
프로필은 변경하지 않는다. 직전 변경 파일만 비공개 `updates/wifi-policy-previous`
아래에 보관하며 배포물에는 포함하지 않는다. 새 이미지에도 기본 절전 해제 값을
명시한다. NetworkManager가 연결·DHCP를 진행 중이면 회복 작업이 별도 UP 요청을
보내 취소하지 않고, 절전 설정 차이만으로 정상 연결을 강제 재접속하지 않는다.

별도의 6분 탁상 시험에서는 Jetson station을 전용 AP BSSID에 고정해도
1초 제한 ping이 317/360회만 응답했다. 같은 동안 USB는 360/360회 정상이었다.
따라서 BSSID 고정을 개선이 입증된 기본값으로 추가하지 않는다. 재접속 중
중복 활성화 기록은 확인했지만 절전 해제 후 모든 무선 손실의 원인은 아직
확정하지 못했다. 이 소스 변경은 새 대응 패키지·실장치 초기 부팅 검증과
구분해야 하며, 주행 중 20Hz·무선 무손실·주행 안전 보장을 뜻하지 않는다.

해당 `16ad17db` 패키지를 실제 설치하고 다시 부팅한 기록에서 절전 유지 작업은
15.42초에 실행됐고, 부팅 정책 완료는 15.92초, 첫 Wi-Fi 연결은 24.61초,
모델 서버 실행은 33.28초였다. 부팅 정책이 모델 서버와 첫 무선 연결보다 먼저
실행됨을 확인했다. 무선 손실이 모두 사라졌다는 검증과는 구분한다.
실장치에서 발견한 완료 표시의 권한도 보완한다. 소스 다이제스트만 담는 완료
파일은 0644, 비밀정보 없는 상태 디렉터리는 0755로 두어 일반 서버 계정이
동일 정책의 설치 완료를 읽고 불필요한 재설치를 피할 수 있게 한다. 비밀번호와
프로필 백업은 계속 비공개이며 권한을 확대하지 않는다.

콤마 AP 유지 작업의 오류 처리도 보완한다. 기존 코드에서는 NetworkManager나
nl80211 상태 조회 한 번의 실패만으로 이미 생성한 AP의 연결을 내리고 인터페이스를
삭제했다. 이제 정상 활성화가 완료된 AP는 조회 실패 시 보존하고 30초 뒤 다시
조회한다. 상태에는 비밀정보 없는 `control_query_failed`를 기록한다. 인터페이스
소유권 상실이 확인되거나 AP가 비활성이라고 확인된 경우에는 기존 정리·복구를
유지한다. 종료·공식 브랜치 전환 시의 자기 소유 AP 정리도 유지한다. 이 콤마 측
변경은 Jetson 모델·USB나 추론 루프를 변경하지 않는다. 실제 RF 손실이 이 예외
처리 경로 때문이었다고 확인한 결과는 아니며, PC 장애 주입으로 정상 AP 보존과
확인된 소유권 상실 시 정리를 각각 검증했다.

추가 드라이버 능동 로밍 비교는 같은 부팅에서 기본값·시험값 각각 180초 모두
180/180회 응답해 개선을 입증하지 못했다. 시험값은 원복하고 배포 기본값에서
제외한다. 보완판 `b21f1f4c` 공개 패키지는 초기 정책과 완료 표시 권한을 포함하며
기존 SHA·모델·복구 검사로 설치한다. 잔여 무선 손실의 원인과 무손실 동작은
여전히 확정하지 않았다.

최종 [공개 패키지 `b21f1f4c`](https://github.com/tjdgus200/openpilot/releases/tag/jetson-pv5-wifi-early-20261022-b21f1f4c)를
콤마 USB로 설치하고 별도로 Jetson을 정상 재부팅했다. 같은 새 부팅에서 절전
유지 작업은 15.943초, 초기 정책 완료는 16.486초, 첫 Wi-Fi 연결은 25.034초,
모델 서버 실행은 33.317초였다. 21.54초의 실제 커널 조회에서도 절전이 꺼져
있었다. 전원 인가 순간부터 값이 항상 꺼져 있다는 검증은 아니며, 첫 연결과
모델 시작보다 먼저 정책이 적용되는 것을 확인한 결과다.

완료 다이제스트와 설치 도구의 내용이 일치했고, 일반 서비스 계정이 0644
완료 파일과 0755 상태 디렉터리를 읽을 수 있었다. 콤마도 별도 정상 재부팅 후
두 무선 인터페이스의 절전 꺼짐과 전용 AP 경로의 자동 복귀를 확인했다.
Jetson 보조 수신기는 직접 Wi-Fi 주소에만 바인딩됐고 가져온 프로필은 하나였다.
모델·HUD 서비스는 실행 중, 재시작 0회였다. 실제 HUD 화면 연결은 이 세션에서
감지되지 않아 물리적 화면 표시까지 확인했다는 뜻은 아니다.

최종 정상 기동 후 120초 탁상 관찰에서 USB는 120/120회 `ready`, 오류 0회,
직접 AP ping은 1초 제한으로 120/120회 응답했다. 응답 지연 평균은 2.66ms,
최대는 33.1ms였다. 별도의 60초 자원 관찰에서 절전 조회 13/13회가 꺼짐이었고
작업자는 nice19/SCHED_OTHER/CPU0-1, 재시작 0회, CPU 한 코어 기준 약 0.0163%,
메모리 약 6.17MiB였다. 이는 유휴 상태의 해당 작업 측정이며 전체 Wi-Fi 비용이나
주행 부하의 측정이 아니다.

[런타임 변경 CI](https://github.com/tjdgus200/openpilot/actions/runs/39720583133)는
루트 계약 103, 확대 검사 1246(61 제외), 내비 119, 저장소 11, 패킷 11개 및
Windows 설치 검사를 통과했다. 마지막 짧은 관찰이 성공해도 이전 긴 관찰의
손실 원인을 규명한 것은 아니다. 주행 모델·제어·USB 추론 경로는 이번 변경의
대상이 아니며, 주행 안전이나 20Hz 유지가 검증됐다고 해석하지 않는다.

## 느린 상태 조회 중의 불필요한 스캔 방지 (2026-10-22)

추가 검토에서는 AP 조회 지연과 선택적 네트워크 검색 사이의 틈을 PC에서
재현했다. AP 관리자의 NetworkManager 명령은 최대 15초를 기다릴 수 있으나,
UI·웹의 검색 억제 힌트는 8초가 지난 상태를 만료로 처리했다. 실제 AP가 계속
살아 있어도 이 동안 배경 검색을 허용할 수 있었다. 상태 기록도 조회 전 시각을
사용해, 느린 조회가 끝난 직후부터 이미 만료된 기록을 내보낼 수 있었다.

이제 관리자는 자신이 생성한 인터페이스 번호(`ifindex`)를 비밀정보 없는 상태에
기록하고, 조회를 마친 시각으로 갱신한다. 활성 힌트가 오래됐더라도 커널의
`/sys/class/net/wljetson0/ifindex`가 그 번호와 같으면 선택적 검색 억제를 유지한다.
인터페이스가 없어지거나 교체됐거나 상태가 비활성이면 해제한다. 이 힌트는
네트워크 검색 억제에만 사용하며 패킷·인증·제어 신선도나 연결 준비 판정을
완화하지 않는다. 추가 NetworkManager 명령·스캔·대기는 없고, 사용자가 UI에서
명시적으로 요청하는 검색도 유지한다.

PC 장애 주입은 정상 AP 조회를 15초 지연시킨 동안 검색 억제와 AP 단일 생성을
확인하고, 교체·누락 인터페이스와 이전 버전의 신선한 상태도 검사했다.
관련 검사 47개 통과, 1개 제외 및 Ruff 통과다. 이 콤마 측 수정은 선택된
Jetson `b21f1f4c` 패키지를 바꾸지 않는다. 이전 실장치 RF 손실이 이 코드 경로
때문이었다고 확인한 것은 아니다. 사용자는 이후 핫스팟을 끄는 시험을 취소했으며,
진행 중인 장시간 관찰은 핫스팟 연결을 유지한 조건이다.

그 관찰은 이후 20분까지 완료했다. 기준은 콤마 `bf5d4b15`, Jetson `b21f1f4c`이며
핫스팟은 계속 켜 두었다. 낮은 우선순위의 별도 관찰기가 양방향으로 1초에 한 번
직접 AP 주소에 ICMP를 보내고 기존 상태를 읽었으며, 카메라·크루즈·주행 부하를
새로 재현하지 않았다.

| 방향 | 응답 | 응답 평균 / P99 / 최대 | 최장 연속 응답 실패 |
| --- | --- | --- | --- |
| 콤마 → Jetson | 1173 / 1200 | 3.60 / 27.1 / 513ms | 19회 |
| Jetson → 콤마 | 1175 / 1200 | 3.66 / 32.4 / 246ms | 19회 |

응답 제한은 1초이며, 응답하지 않은 패킷은 위 지연 통계에서 제외했다. USB는
1200/1200회 `ready`, 오류 0회였고 AP 관리자의 상태 조회 오류도 0회였다.
양쪽 모두 41회 절전 조회가 꺼짐이었다. Jetson의 실제 무선 연결 해제 이벤트
한 번과 약 9.52초 뒤 재연결을 확인했다. 데이터 손실은 그 이벤트보다 먼저
시작했으며, 다른 짧은 손실 구간에는 연결 해제 이벤트가 없었다. 이 결과는
문제 범위를 무선 링크·데이터 경로로 좁히지만, 어느 드라이버나 전파 조건이
원인인지를 확정하지는 않는다. 실제 끊김을 AP 조회 예외나 절전 재활성화로
단정할 근거도 없다.

별도의 6분 읽기 전용 관찰에서 LPS 진입 카운터는 0, IPS 진입·복귀 카운터는
3으로 유지됐다. 이 추가 기록은 첫 긴 연결 해제 구간과 겹치지 않았으므로
절전 진입이 그 끊김보다 먼저였는지 뒤였는지를 입증하지 못한다. 경고 문자열만
보고 커널이나 드라이버 설정을 변경하지 않는다.

[콤마 보완 `f1943693`](https://github.com/tjdgus200/openpilot/commit/f194369317998b97bbf5eab4ef7e15b73e105afa)은
이 측정이 끝난 뒤 설치하고 정상 재부팅했다. 실제 커널 인터페이스 번호 일치,
오래된 검색 억제 힌트 유지, 교체된 인터페이스 거부를 장치에서 읽기 전용으로
확인했다. AP 작업자는 nice19/SCHED_OTHER/CPU0-3으로 실행됐고, Jetson 소스·부팅과
모델·HUD 서비스의 재시작 0회는 유지됐다. 그 뒤 120초 확인에서도 USB는
120/120회 정상이었으나 Wi-Fi 응답은 116/120회였다. **스캔 억제 보완은 별도로
재현한 코드 문제의 수정이며, 실제 RF 손실이 해결되거나 개선됐다는 결과가 아니다.**

[해당 변경 CI](https://github.com/tjdgus200/openpilot/actions/runs/39722899806)는
루트 103, 확대 검사 1257(61 제외), 내비 119, 저장소 11, 패킷 11개 및 Windows를
통과했다. 로컬 관련 검사는 107개 통과·1개 제외와 Ruff 통과다. 새 Jetson 배포물은
만들지 않고 기존 `b21f1f4c`를 유지했으며, 커널·드라이버·모델·주행 제어·USB 추론
경로는 변경하지 않았다. 핫스팟 OFF, 실차 안전 또는 주행 부하 20Hz를 검증한
결과로 해석하지 않는다.

## 핫스팟 유지 상태의 무선 계층 구분 (2026-10-22 후속)

콤마 `a1992a43`, Jetson `b21f1f4c`의 탁상·오프로드에서 휴대폰 핫스팟을 계속
켜 두고 다시 관찰했다. 콤마→Jetson 직접 AP, 반대 방향, 콤마→휴대폰 업링크를
별도로 읽었다. 10분 무부하 기준 관찰에서 직접 AP 응답은 598/600회
(응답 평균 3.69/P99 26.1/최대 80.3ms), 반대 방향은 600/600회
(2.66/13.2/25.7ms), 휴대폰 업링크는 599/600회였다. USB는 600/600회
`ready`, 오류 0회였다. 응답 제한은 1초이며 미응답은 지연 통계에서 제외했다.

이어 별도 직접 AP 진단 포트에서 512KiB의 합성 TCP 레코드를 목표 2Hz로 보냈다.
성공할 때의 목표 페이로드 전송률은 약 8.4Mb/s이며 실제 실패·대기로 전송률은
낮아진다. 실제 영상·제어·지도·모델 입력을 넣은 시험이 아니다. 이 레코드는
실제 보조 RPC의 단일 요청 상한 380,000바이트보다 크므로, 실제 ONNX 요청의
성능 측정이나 동일 부하 재현으로 해석하지 않는다. 모델·공식 직렬 USB 추론은
변경하지 않았다.

첫 송신은 134초 동안 139개 시도 중 15개만 완료했고 직접 링크의 긴 응답 실패가
재현됐다. Jetson에서 첫 데이터 손실 뒤 비콘 수신 0, 스캔 상태와 재연결을
관찰했다. 콤마 커널에는 그 단말에 대한 `wma_peer_sta_kickout_event_handler`
이벤트가 있었다. 손실·중단·후속 버퍼/분산 시험을 포함한 다음 10분 관찰에서는
직접 AP 245/600, 휴대폰 598/600, USB `ready` 600/600·오류 0이었다. 이 구간은
**여러 조건이 섞인 관찰이며 단일 설정의 10분 A/B 결과가 아니다.**

| 임시 비교 조건 | 합성 TCP 완료 / 시도 | 송신 관찰 길이 |
| --- | ---: | ---: |
| 기본 소켓 | 15 / 139 | 134.0초 |
| 송신 버퍼 64KiB | 172 / 240 | 157.4초 |
| 8KiB 조각을 4ms 간격으로 분산 | 27 / 175 | 169.2초 |
| Jetson RX A-MPDU 수락 일시 해제 | 48 / 125 | 106.9초 |
| Jetson 능동 로밍만 일시 해제 | 116 / 246 | 201.7초 |

시간·초기 연결 상태가 다르고 앞선 장애의 회복이 겹치므로 이 비율로 조건의
우열이나 인과 효과를 순위 매기지 않는다. 분산 송신의 조각별 타임아웃도 실제
RPC 전체 마감과 다르다. **어느 조건에서도 장애 제거가 확인되지 않아 모두
기본 적용을 거부했다.** 전송을 중단한 뒤 회복도 관찰했으나, 전파 변화나
연결 회복 시간의 영향까지 배제한 원인 증명은 아니다.

이번 장치의 드라이버는 `rtl8822ce` 버전
`v5.14.0.4-250-g5d0d248cc.20240517_COEX20240327-2727`였다. PCIe 실제
Link Control의 ASPM은 비활성, 런타임 전원은 active/on이었다. 무선 절전은
꺼짐이었고 LPS 진입 수는 0, 관찰한 펌웨어 재설정/전원 오류 카운터도 0이었다.
첫 손실 때 IPS 카운터는 그대로였고 나중에 증가했다. 즉 이 재현에서 절전
진입을 선행 원인으로 지목할 증거는 없다. 현재 연결의 콤마 업링크와 Jetson
직접 링크는 모두 5745MHz였으므로 이 시점의 서로 다른 채널 사용도 확인되지
않았다. 강한 RSSI나 이전 검색 캐시만으로 RF 간섭을 배제하지 않는다.

확인된 범위는 직접 무선 링크의 부하 관련 단절·단말 퇴출이다. 이것이 특정
드라이버 결함인지, 두 무선 칩의 호환성인지, 전파 간섭인지의 최종 구분은
미완료다. 단말 퇴출 메시지 자체가 드라이버 충돌·인증 실패를 증명하지 않는다.
커널/펌웨어 교체, 재전송/유효시간 완화 또는 라디오 강제 재시작으로 숨기지 않는다.

집성·로밍 비교에는 장치 자체의 제한 시간 원복과 오프로드 확인을 걸었다.
끝난 뒤 RX 집성 `accept=1(auto)`, 고정 값 `255/255`, 로밍 `0x07` 복귀를
실제로 읽어 확인했다. 모델·HUD 서비스는 active/재시작 0회였고 USB도 정상이다.
이번 결과로 새 무선 기본값이나 Jetson 배포물을 만들지 않으며 선택된
`b21f1f4c` 패키지를 유지한다. 실제 주행 안전·20Hz 또는 화면 표시를 검증한
결과는 아니다. 원문 저널·개인 무선 식별자·차량 페이로드는 공개하지 않는다.
