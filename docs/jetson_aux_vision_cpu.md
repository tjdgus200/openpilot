# carrot-nav-pv5: CPU 차선·BSD와 Wi-Fi

`ShareData`의 기존 차선 종류 분류와 `OnnxBsdEnabled`의 시각 BSD ONNX 계산을
Jetson CPU로 옮긴다. 두 설정은 기본 OFF와 기존 온로드 준비 조건을 유지한다.
차량 BSD, 분류 클래스·임계값·ROI·평활화, 차선변경 제어 조건과 N16 주행 모델은
유지한다. 이 변경은 별도의 전방 차량 거리/위치 검출기를 추가하지 않는다.

## 데이터와 실행

- 콤마는 기존 회색조 차선 입력과 마스크/레터박스 BSD 입력을 만든다. 입력은
  각각 uint8 416×416, 352×352×3이다. JPEG 재압축 없이 같은 픽셀을 보낸다.
- 영상과 결과는 **직접 Wi-Fi AP의 TCP 7717**만 사용한다. 콤마의 `wljetson0`
  게이트웨이 주소, 같은 전용 /24의 Jetson 주소, 실제 출력 장치와 중간 게이트웨이가
  없는 경로를 매 요청 확인한다. 휴대폰 핫스팟/공유기·USB/NCM/이더넷 우회는 금지한다.
- USB에서는 세션 시작 때 지원 기능과 임시 키만 협상한다. 기존 HUD와 주행 모델의
  공식 USB 경로는 유지한다. 보조 영상은 주행 모델 USB 프레임에 넣지 않는다.
- 기존 인증 교환에서 용도가 분리된 키를 만들고 AES-GCM, 순서 번호, 요청 ID와
  ONNX SHA-256으로 상대·결과를 확인한다. 키를 명령행/상태/로그에 기록하지 않는다.
- 양쪽에 별도 보조 작업을 둔다. Jetson은 OpenCV DNN CPU 백엔드/타깃, OpenCL OFF,
  OpenCV/BLAS 스레드 1개, 일반 스케줄링 nice10, 허용 CPU 중 앞의 최대 2개를 쓴다.
  콤마 릴레이와 영상 전처리는 일반 우선순위 nice19로 실행한다. 주행 GPU 계산이나
  제어 스레드의 우선순위를 바꾸지 않는다.

## 부하와 유효성

- 초기 차선 간격은 500ms, BSD는 **좌우 합산** 500ms다. 양쪽이 설정되면 각 방향은
  번갈아 처리하므로 최대 1Hz다. 더 짧은 기존 저장값은 실행할 때만 500ms로 제한하고
  저장값을 덮어쓰지 않는다. 반복/후속 감지를 더 빠르게 실행하지 않는다.
- 동시 계산은 1개, 각 연결 대기열은 1개, 요청은 최대 380,000바이트, 응답은 최대
  4,096바이트다. 콤마의 전체 RPC 마감은 750ms다. Jetson은 이전 계산 시간의
  1/4만큼 다음 계산을 쉬어 단일 CPU 스레드의 지속 점유를 제한한다. 이는 공유
  메모리·전력 간섭까지 격리하는 cgroup 보장이나 20Hz 동작 보장은 아니다.
- 원시 입력만 계산하면 최대 약 8.72Mbit/s이며 인증·전송·재시도 비용은 별도다.
  실제 속도를 측정한 수치가 아니다. CPU와 Wi-Fi가 느리면 요청률은 더 낮아진다.
- 결과 시각은 콤마의 원래 카메라 촬영 시각이다. 미리 250ms 이상 지난 영상과
  미래 시각은 보내지 않는다. 원격 차선은 촬영 후 1초, BSD는 기존 1.5초 이내에서만
  사용한다. Jetson과 콤마의 서로 다른 시계를 비교하거나 완료 시각으로 나이를
  초기화하지 않는다. 단절/지연/해시 불일치는 unknown이며 로컬 ONNX fallback은 없다.
  응답 없는 연결은 5초 유휴 제한으로 닫아 재연결이 막히지 않게 한다.
- BSD OFF는 기존 세대 번호/동시 갱신 보호를 유지하고 콤마 결과를 즉시 무효화한다.
  원격 모델 해제를 요청하고, 호스트에서도 3초간 쓰이지 않은 모델을 해제한다.
  프로세스/할당기 캐시 때문에 RSS가 즉시 같은 크기로 줄어든다는 뜻은 아니다.
  차량이 제공한 BSD를 원격의 false 결과로 지우지 않는다.
- 이 이식은 기존 차선변경 제어 정책을 대체하지 않는다. 원격 응답 없음은 안전한
  차선이라는 판정이 아니며 운전자가 주변과 기존 차량 경고를 확인해야 한다.

## 설치와 확인

콤마와 대응 Jetson 런타임을 함께 업데이트해야 한다. 기존 SHA USB 수신기를
등록한 장치는 콤마 브랜치 업데이트 후 Jetson 정상 재부팅으로 새 묶음을 받는다.
P단/정지 조건, SHA/크기/ABI 검사, 공식 NAS 서명 복귀 경로는 유지한다.
처음 받는 파일은 콤마의 인터넷 또는 검증된 캐시가 필요하다.

이 브랜치는 [공개 대응 패키지](https://github.com/tjdgus200/openpilot/releases/tag/jetson-pv5-aux-wifi-20261021-c56183fd)를
선택한다. 소스 `c56183fd`, 81,667,195바이트이며 SHA-256은
`40688dad244c63683b232de766a13e4812b06b19ff6ecae8a19597759161a849`다.
공개 HTTPS 재다운로드로 검증했다. 공식 N16 파일은 변경하지 않았고 묶음에
주행 모델을 다시 포함하지 않는다. 콤마만 업데이트하면 이전 Jetson이 CPU 기능을
자동으로 갖는 것이 아니며, 정상 부팅 수신기가 이 대응 묶음을 설치해야 한다.

호스트 묶음에는 기존 두 ONNX와 CPU 소스를 포함한다. OpenCV가 필요하며 새 설치의
`requirements-jetson.txt`는 NumPy 1.26과 호환되는 CPU wheel 4.10.0.84를 지정한다.
이미 실행 가능한 OpenCV가 있으면 설치 중 강제로 교체하지 않는다. 설치 전 별도
CPU 자식 프로세스에서 두 모델을 로드/실행하고 메모리를 반환한 후 기존 주행 GPU
검사를 실행한다. 의존성/실행 검사가 실패하면 기존 릴리스를 유지한다.

캐럿 웹의 기존 상세 상태는 `processor=jetson_cpu_wifi`, `transport=wifi`를 보고하고
실제 최근 원격 응답이 있어야 모델 준비 완료로 표시한다. 오래된 호스트는 지원
기능을 광고하지 않으므로 영상 전송과 콤마의 대체 ONNX를 시작하지 않는다.

PC 검사는 실제 두 ONNX의 로컬/원격 입력 결과, 인증·재전송/변조 거부, 입력 크기와
순서, 잘못된 모델/상대/응답, 차량 BSD 보존, 촬영 시각, 원래 BSD ON/OFF 동시성,
ROI·스냅샷·NV12 전처리를 포함한다. 네이티브 IPC는 명시적인 import용 대체 구현과
테스트 소켓을 사용하며 실제 CAN/카메라/차량 제어나 GPU 성능 검증으로 세지 않는다.
이번 브랜치의 온로드·크루즈·유효 맵과 동시 실행한 실기기 20Hz 측정은 별도다.

## 실패 진단과 표시

차선 `lane.diagnostic`, BSD `model.diagnostic`와 웹 상단의 두 진단 행은 고정된
`code`/`stage`/설명을 제공한다. 실제 요청·성공·실패·진행 중 횟수도 구분한다.
기존 차선 `inference.count`는 실패 결과까지 포함하는 시도 횟수이므로
`countKind=attempts`로 명시한다. 시간 값과 요청 FPS만으로 추론 성공을 판단하지 않는다.

| 분류 | 대표 코드 | 확인한 범위 |
| --- | --- | --- |
| 구버전/설치 | `runtime_outdated`, `runtime_incomplete` | 기능 미광고와 기능 사용 불가를 구분. 미광고가 아닌 false만으로 구버전이라고 단정하지 않음 |
| 의존성/모델 | `dependency_missing`, `model_missing`, `model_load_failed`, `model_hash_mismatch` | 지원되는 새 호스트가 확인한 OpenCV·모델 로드·해시 문제 |
| 세션/릴레이 | `session_setup_timeout`, `session_setup_rejected`, `relay_start_failed`, `relay_unavailable` | USB의 초기 세션 협상과 콤마의 별도 릴레이 시작 상태 |
| Wi-Fi | `wifi_local_unavailable`, `wifi_peer_unavailable`, `wifi_route_unavailable`, `wifi_connect_failed` | 로컬 주소, 신선한 상대 주소, 실제 WLAN 경로, 접속 실패를 구분 |
| 인증 | `authentication_failed`, `authentication_timeout` | HMAC/AEAD 거부와 인증 대기 시간 초과를 구분. 시간 초과만으로 키 불일치라고 단정하지 않음 |
| 추론 | `inference_failed`, `inference_invalid_result` | 인증된 요청의 호스트 계산 실패와 결과 형식/유한값 오류 |
| 미확정 | `response_timeout`, `remote_closed` | 응답 시간 초과/연결 종료만으로 무선·CPU 계산 중 어느 원인인지 단정할 수 없음 |

BSD 원격 실패는 카메라 단절로 기록하지 않으며 VisionIPC 연결을 유지한다.
영상 나이와 카메라 오류는 별도로 표시하고, 실패한 BSD 결과는 무효화한다.
차량 고유 BSD와 기존 unknown/유효시간 정책은 유지한다. 실패 재시도도 기존
좌우 합산 500ms 제한을 따르며 빠른 반복/추가 추론을 만들지 않는다.

호스트의 상세 오류는 USB HELLO의 `carrot_aux_cpu_diagnostics_v1`으로 구분한다.
인증 및 AEAD 복호화, 요청 ID/해시 검사를 통과한 오류 응답만 받는다. 오류 응답은
`valid=false`이며 차선 없음/차 없음 결과로 바꾸지 않는다. 모든 상태는 허용한
고정 코드만 전달한다. OpenCV 원문·입력 영상·네트워크 비밀·키·환경변수는 상태에
포함하지 않는다. 구형 CPU 호스트에는 상세 진단 미지원이 표시되며, 그 호스트가
단순히 연결을 닫은 경우 추론 오류라고 추측하지 않는다.

새 상세 진단의 완전한 사용에는 대응 Jetson 패키지도 업데이트해야 한다.
콤마 Git Pull/정상 재부팅과 Jetson 정상 재부팅을 사용하는 기존 경로다.
단순 표시 개선으로 Wi-Fi 안정성·주행 인식·20Hz가 검증됐다는 뜻은 아니다.

[진단 소스 CI](https://github.com/tjdgus200/openpilot/actions/runs/39565949638)는
루트 수신/복구 103개, 넓은 통합 검사 1,212개(선택적 61개 건너뜀), 내비/장면
119개, 실제 격리 파일시스템 11개와 격리 Wi-Fi 패킷 11개 및 Windows 디스크
선택 검사를 통과했다. 중복을 포함하므로 고유 검사 수로 합산하지 않는다.
PC에서 실제 로컬 소켓과 인증/암호화 소켓의 오류 전달·변조 거부, 실제 두 ONNX,
카메라 연결 유지·BSD OFF 동시성·전처리를 검사했다. Linux의 Node 없는 검사는
건너뛰되 Windows Node에서 실제 웹 스크립트 문법과 KO/EN/ZH 진단 렌더 함수를
별도로 실행했다. 최종 설치 묶음은 안전하게 격리 추출한 뒤 두 CPU 모델과 HUD
진입점을 실행하고 공개 HTTPS 전체 재다운로드의 크기/SHA도 확인했다.

## 듀얼 Wi-Fi 코드 확인

`wifi_direct_netlink.py`는 `wlan0`와 같은 PHY에 별도 `wljetson0` AP를 만들기 전에
드라이버의 동시 station/AP 조합 지원을 확인한다. `wifi_direct.py`는 기존 `wlan0`
프로필을 바꾸지 않는다. 사용자 후속 요청에 따라 **온로드 부팅에서도 AP를 자동 생성/
복구**하며, 활성 AP는 온로드에도 유지한다. 따라서 휴대폰을 콤마의 AP로 쓰는 구조가 아니라
`wlan0 → 휴대폰`과 `wljetson0 AP → Jetson`을 함께 사용하는 구조를 지원한다.
한 PHY의 가상 인터페이스이므로 독립된 두 무선 장치가 있다는 뜻은 아니다.

사용자 추가 요청으로 이 브랜치는 **직접 AP만 허용**한다. `wifi_publisher.py`는
소유한 활성 AP 한 개만 읽어 `wifi_policy=direct_only`와 실제 AP 서브넷을 개인 USB
채널로 전달한다. 휴대폰과 기타 저장 프로필의 암호를 읽거나 Jetson에 보내지 않는다.
AP가 없으면 프로필은 빈 값이며 공용 WLAN으로 바꾸지 않는다. 이미 활성화된 AP의
SSID·암호·클라이언트 식별자는 휴대폰 접속/해제로 바뀌지 않는다. 기존 독립 네트워크
수신기는 새 AP 연결 확인 뒤 이전 콤마가 관리하던 핫스팟 프로필을 제거한다.
관리자가 직접 저장한 프로필은 지우지 않지만 보조 데이터 경로에는 사용할 수 없다.

Jetson의 새 수신 작업은 USB로 전달된 프로필로 계산한 NetworkManager UUID와
현재 장치가 일치하고 그 주소가 전용 서브넷인 경우에만 수신 소켓을 연다. 상대도
그 AP의 콤마 게이트웨이 주소여야 하며 기존 세션 인증을 유지한다. 휴대폰 주소가
생기거나 사라져도 이 수신 주소 목록을 바꾸지 않는다. Wi-Fi HUD를 협상하는 구형
화면 경로에도 같은 제한을 적용한다. 현재 공식 USB HUD와 주행 모델·업데이트·초기
Wi-Fi 정보 전달의 USB 경로를 Wi-Fi로 옮기는 변경은 아니다.

휴대폰은 콤마 `wlan0`의 인터넷 업링크로만 쓴다. Jetson이 인터넷이 필요하면 기존
전용 AP의 NAT를 거쳐 콤마 업링크를 사용한다. 핫스팟이 꺼져도 AP를 내리지 않으며
인터넷 공유 설정 실패는 로컬 AP를 종료하지 않는다. AP 절전 해제도 유지한다.
보호 OS/독립 복구 서비스를 교체하거나 새 관리자 권한을 추가하지 않는다.

`diagnostic.wifiPath`와 웹 진단 행은 최근 검증된 응답 경로만 `direct_ap`로 표시한다.
이전 버전이 보고한 `shared_wifi`의 표시 호환성만 남긴다. 3초 이상 관측이 없으면
`unknown`이며, 무응답 동안 예전
경로를 현재 연결 보장처럼 표시하지 않는다. AP 활성화와 DHCP가 끝나기 전,
드라이버/채널 제약 또는 RF 문제로 직접 연결이 준비되지 않을 수 있다. 코드 검사와
PC 회귀에서는 직접 AP만 선택·공용 WLAN/다른 서브넷/경유 라우트 거부,
핫스팟 해제·복귀 시 프로필/수신 주소 유지와 기존 네트워크 수신기 호환성을 검사한다.
격리 Linux veth 시험은 실제 라우트와 패킷으로 업링크 해제 중 직접 경로를 검사한다.
물리적 장치의 동시 연결·채널 변경·주행 중 회복을 측정한 결과는 아니다. 단일 PHY의
드라이버가 AP+STA를 동시에 유지하지 못하거나 RF가 끊기면 소프트웨어가 무선을
보장할 수 없다. 이때 핫스팟으로 우회하지 않고 오류/unknown으로 표시한다.

선택한 PC 회귀는 220개 통과, 선택적 2개는 별도 환경 조건으로 생략했다.
웹 진단은 Windows Node에서 별도로 실행했고, 격리 Linux의 실제 네트워크 패킷
검사 11개도 통과했다. 이 숫자는 중복을 포함하며 실제 RF/장치 설치 결과가 아니다.

## 핫스팟 없는 온로드 부팅

전용 AP 생성/재연결에서 `IsOffroad` 제한을 제거했다. 콤마와 Jetson의 USB 제어
연결이 준비되면 기존 개인 채널로 전용 AP 정보가 전달되고 Jetson의 독립 네트워크
수신기가 자동 연결한다. 휴대폰 핫스팟을 켜거나 온로드/기어 상태를 조작할 필요는 없다.
AP가 준비되기 전에도 USB 업데이트 제어 패킷은 계속 전달한다. 준비 전 프로필 확인은
5초 간격이며, 정상 AP 확인 뒤에는 30초 간격으로 줄인다. 주 루프는 2초 단위이므로
실제 확인은 해당 간격 이후 처음 순회에서 진행한다. AP/NM/DHCP와 Jetson의 기존
재시도 간격이 필요하므로 부팅 순간의 0초 연결을 약속하는 기능은 아니다.

AP와 프로필 전달 작업은 별도 프로세스에서 SCHED_OTHER/nice19, 코어 0–3으로
실행한다. AP 시작/복구의 NetworkManager 대기나 실패가 주행 모델 프레임 경로를
기다리게 하지 않는다. 실패한 활성화는 30초 뒤 재시도하고, 활성 AP는 5초 간격으로
확인하며 다시 만들지 않는다. 채널은 기존 스캔 캐시만 읽고 핫스팟이 없으면 기존
5GHz 채널 36 선택을 사용한다. 강제 스캔·휴대폰 프로필 재접속·전체 Wi-Fi 라디오
토글·USB 재설정·주행 작업의 코어/우선순위 변경은 추가하지 않는다. 별도 NAT 보정은
계속 오프로드에서만 실행하며, 보정 실패 때문에 로컬 AP를 종료하지 않는다.

PC 검사에서 온로드/핫스팟 없음 AP 활성화, 준비 지연 후 자동 설정 전달, 30초 실패
재시도와 정상 AP 유지, 별도 실행·우선순위·소유 자원 한정을 확인한다. 모의 NM과
Linux 격리 패킷은 실제 무선 펌웨어의 지연이나 CPU/GPU 부하 측정이 아니다.
모델·CAN/크루즈·결과 유효성·공식 직렬 USB는 유지하지만 공유 PHY/커널 자원 때문에
실제 주행에 영향이 전혀 없다는 보장은 할 수 없으며 장치 측정이 필요하다.

이 시작 조건 변경은 콤마 Git Pull/정상 재부팅으로 적용한다. 기존 대응 호스트
`61878ca0`와 USB 프로필/인증 형식은 같으므로 이 변경 때문에 Jetson 패키지를
다시 설치할 필요는 없다. 아직 대응 패키지가 없는 장치는 앞 절의 설치가 먼저 필요하다.

## 설치 검사의 낮은 CPU 우선순위 유지

부팅 업데이터는 nice19로 실행되고, `runuser -u jetlink`로 실행하는 후보 검사와
그 자식 CPU ONNX 검사에도 이 값이 전달된다. 기존 `vision_cpu.py --check-models`는
일반 계정에서 nice10을 요청해 CPU 우선순위를 높이려 했으므로, 기본 Linux 권한에서
모델 로딩 전에 `PermissionError`로 종료될 수 있었다. 콤마에는 후보 활성화 실패
요약만 전달되므로 이 오류가 USB 인증 실패로 보일 수 있지만 별도 문제다.

CPU 보조 작업은 요청값과 상속값 중 더 낮은 우선순위(더 큰 nice 값)를 선택한다.
일반 시작의 송신 nice19/수신 nice10은 같고, 이미 nice19인 설치 검사는 nice19를
유지한다. SCHED_OTHER 전환, 두 CPU 코어 한정, 한 계산 스레드와 CUDA 비활성화는
유지한다. 관리자 권한·스케줄링 능력을 추가하거나 예외를 무시하지 않는다.

기존 공개 패키지의 함수는 Linux 비관리자 자식에서 nice0 시작은 통과했지만
nice19 시작은 권한 오류로 재현됐다. 수정 함수는 nice19를 유지하며 통과한다.
당시 패키지는 실제 두 CPU ONNX 검사, HUD 진입점과 GPU 후보 검사를 필수로 실행했다.
아래 후속 변경에서는 설치 시 CPU ONNX 실행 검사만 제거했다.
PC 재현은 사용자의 Jetson 내부 오류 기록이나 주행 안정성 검증을 대신하지 않는다.

Jetson에서 실행되는 파일이므로 수정된 호스트 패키지가 필요하다. 콤마의 이
브랜치를 Git Pull/재부팅하고 USB를 유지한 채 Jetson도 정상 재부팅하는 기존
설치 경로를 사용한다. 기존 수신 허용 정책·키·SHA 검사·P단/정차 승인과 이전
릴리스 보존은 유지하며, 실행 중인 주행 엔진을 교체하지 않는다.

수정된 대응 호스트의 소스는 `4e3acd5e05f5be51c109265d8973f8c96de6e599`이며,
공개 패키지는 [설치 검사 우선순위 수정 Release](https://github.com/tjdgus200/openpilot/releases/tag/jetson-pv5-install-priority-20261021-4e3acd5e)에 있다.
`usb_host_sha256_release.json`은 이 패키지의 81,665,759바이트와 SHA-256
`cec20f4f924c4dab2f789936860d448322933c853bb330a18e326155f4144440`을 고정한다.
주행 모델의 SHA/크기와 ARM64·L4T·TensorRT 조건은 기존 선택과 같다.
이전 runtime-port 수신기의 명세 검사도 통과한다. 패키지·체크섬·메타데이터·USB
명세를 인증 없는 공개 HTTPS 주소에서 모두 다시 내려받아 로컬 파일과 비교했다.

공개 아카이브에서 추출한 실제 차선·BSD 두 ONNX를 비관리자 nice19 자식으로
검사했고, 종료 때 nice19/SCHED_OTHER 유지와 HUD의 실제 `--help` 진입점도 확인했다.
관련 PC 회귀 164개가 통과했고 선택 검사 1개는 생략했다. 소스 커밋의
[GitHub Actions](https://github.com/tjdgus200/openpilot/actions/runs/39594324792)도 통과했다.
이 배포 준비 검사는 실제 Jetson의 설치 완료·GPU 실행·무선 지연·주행 검증을
의미하지 않는다. 장치는 기존 후보 실행 검사를 통과해야 새 버전으로 전환한다.

## 재부팅 조사 중 설치 시 CPU 모델 실행 검사 제거

사용자가 검증 도중 BOOT 시간이 초기화되는 전체 재부팅을 보고했다. 콤마 상태에는
기존 Jetson 소스 `0320f54d`가 응답한 뒤 검증 상태에서 USB 연결이 사라지는 것이
관측됐다. 커널·전원 기록은 확보하지 못했으므로 CPU 검사 때문에 재부팅됐다고
확정하지 않는다. 사용자 요청으로 활성화 전 `vision_cpu.py --check-models` 호출을
제거하며, 이 진입점은 기존 `0320f54d`의 검사 코드와 같아진다.

패키지 SHA/길이·모델 계약·런타임·수신 허용 정책 검사, 실제 HUD 시작 검사와
GPU 엔진 로드/준비·3회 유한 출력 검사는 유지한다. 실패 시 이전 릴리스 복구도
그대로다. 차선/BSD 모델 파일·Wi-Fi 전송·CPU 작업자·결과 유효성 처리는 유지한다.
보조 ONNX가 실행 시 실패하면 기존 오류/무효 결과 처리를 사용한다. 따라서 설치
성공 자체가 보조 CPU 모델 실행 성공을 보증하지는 않는다. 수동 `--check-models`
진입점은 남기되 부팅 활성화 검사에서 자동 실행하지 않는다.

PC 검사는 실제 후보 검사 진입점에 GPU 대역을 연결해 HUD 실패·엔진 로드 실패·
모델 계약 불일치·비유한/빈 출력이 계속 설치를 거부하는지 확인한다. 이는 실제
Jetson의 GPU 실행이나 재부팅 해결을 입증하는 검사가 아니다. 새 대응 패키지가
필요하며 콤마 Git Pull/재부팅과 USB 연결을 유지한 Jetson 정상 재부팅으로 전달한다.
