# 모델 여유 시간에 따른 HUD 갱신

사용자는 추론에 여유가 있는데도 ‘콤마 데이터 연결 대기’가 자주 또는 계속
나온다고 보고했다. 실물 로그로 원인이 확정된 것은 아니지만 코드에서 아래
두 가지 HUD 기아 경로를 재현했다.

- 모델 요청까지 여유가 남아도 2ms 스냅샷 구간이 끝나면 읽은 패킷을 버렸다.
  반복해서 3~10ms가 걸리는 읽기는 계속 표시되지 않을 수 있었다.
- 지도/미디어 비용과 HUD 스냅샷 비용을 합산했고 대기 상태도 공유했다.
  느린 지도 조각이 작고 빠른 HUD 패킷까지 막을 수 있었다.

## 새 전송 조건

모델 요청 → 필수 지도 입력 → 결과 수신·검사 → 콤마 IPC 응답을 먼저 끝낸다.
그 뒤 또는 유휴 구간에서만 최신 HUD 스냅샷 하나를 보낸다.

1. 모델 요청의 일부 헤더라도 대기 중이면 표시를 시작하지 않는다.
2. 읽기 전에는 예상 읽기+쓰기 비용과 다음 요청 전 4ms 여유를 남긴다.
3. 실제 남은 시간에 따라 스냅샷 시작 허용 구간을 최대 12ms로 잡는다.
4. 읽기 뒤에는 요청 도착과 남은 시간을 다시 검사한다. 이미 사용한 읽기
   비용을 중복 예약하지 않고 아직 남은 USB 쓰기 비용을 확인한다.
5. 지도는 별도 2ms 구간·비용·대기를 사용한다. 지도 정체로 HUD를 중단하지 않는다.
6. 예상보다 긴 HUD 처리나 요청 경계 침범 뒤에는 기존 한 모델 주기 대기를
   유지한다. 완료되지 않은 USB 메시지는 임의 취소하지 않는다.

GPU ms만으로 전송을 강제하지 않는다. 실제 콤마↔Jetson 교환과 USB 쓰기에도
시간이 필요하다. 패킷/차량/경고 TTL과 요청·출력·큐·reset 계약은 유지한다.
새 주기 통계, 비교 화면, 모델 재추론이나 대기 큐는 추가하지 않는다.

## PC 검증

60초 동안 20Hz 모델 입력을 모사하며 HUD 설정 10/15/20/25/30 각각을 검사한다.
모델 처리 25/30/35ms, 스냅샷 읽기 3/8ms, 쓰기 2/3ms의 여유 조건에서
모든 HUD 쓰기가 다음 모델 시점보다 4ms 이상 앞서 완료되고 수신 간격이
300ms 미만인지 검사한다. 부분 모델 요청·읽기 중 요청·느린 지도·오래 걸린
스냅샷·실제 USB 오류·미디어 조각 순서와 기존 60초 dropout 검사도 유지한다.

실제 차량/Orin/USB 검증은 하지 않았다. 이 변경은 확인된 스케줄러 기아를
제거하는 것이며, producer/CAN/케이블/수신 장치가 멈춘 경우의 정상 정보 표시를
보장하지 않는다. 공유 동기 USB의 물리적 무간섭 보장도 별도 검증 대상이다.
