# Jetson Orin 기능 반영 제안 및 실측 결과

기준: 공식 `carrot-nav` 커밋 `8abfa30c5a9b365a4a6aee335ecdd8f3652bddad`.
이 브랜치는 기존 실험 이력을 합친 검토용 변경이며, 즉시 배포용 모델/호스트 선택을 바꾸지 않는다.
개인 배포 manifest·키, 임시 로그 전송, 개인 장치 주소, 추가 자동 테스트 파일은 포함하지 않는다.
기존 공식 테스트 파일은 삭제하지 않는다. 설치 전 실행 검사는 업데이트 기능의 일부로 유지한다.

## 기능과 반영 판단

| 기능 | 변경 내용 | 현재 판단 |
| --- | --- | --- |
| GPU 내부 상태 유지 | 매 프레임 recurrent state의 CPU 왕복을 GPU 복사로 대체하고, 상태 유한값 검사 후 결과 준비 이벤트를 기록 | 실제 Orin에서 작동. 결합 측정에서 Jetson 처리 시간이 감소했으나 단독 반복 비교는 남음 |
| 비동기 USB 송신 | 기존 FunctionFS 프레이밍을 유지하면서 32KiB 요청, 최대 1MiB 대기열로 전송 | 실제 C3에서 작동. 통신·IPC 잔여 지연 개선은 입증되지 않아 기본 활성화 권장하지 않음 |
| 콤마→Jetson USB 업데이트 | 콤마가 서명된 호스트/모델을 캐시하고 부팅 중 Jetson에 전달 | 실제 USB 전송·설치 성공. 공식 NAS와 별도 키/선택 경로로 분리 |

두 성능 경로는 독립적으로 선택한다. 환경변수 `CARROT_TRT_DEVICE_STATE=1`은
Jetson 상태 유지, `CARROT_JETLINK_AIO_WRITE=1`은 콤마 비동기 송신을 켠다.
이 브랜치는 `runtime_port_options.json`을 넣지 않아 둘 다 기본 꺼짐이다.
배포자가 릴리스 범위의 설정 파일을 추가할 경우 다음 형식을 사용하며, 명시적인 환경변수 `0`이 우선한다.

```json
{
  "CARROT_TRT_DEVICE_STATE": true,
  "CARROT_JETLINK_AIO_WRITE": false
}
```

이는 배포 시 선택 예시이지 이 조합의 실차 검증 완료 선언이 아니다. GPU 단독/AIO 단독을
동일 조건에서 번갈아 반복 측정하고 재연결·메모리 압박·전원 중단을 검증한 뒤 활성화 여부를 정해야 한다.
상태·주행 출력의 유한값 검사, 모델 일치, 시간 제한, 프레임/pose 유효성 조건은 완화하지 않는다.
이전 결과를 재사용해 처리율을 높이는 정책은 가져오지 않았다. AMD eGPU 추론 경로는 변경하지 않는다.

## 구현 시 해결한 호환성 문제

- C3 FunctionFS는 성공한 AIO 완료의 바이트 수를 `res2`에도 넣는다. 제출 길이와 `res`가
  정확히 일치할 때만 `res2=0` 또는 `res2=res`를 허용한다. 짧은 전송/오류/알 수 없는 토큰은 계속 거부한다.
- CUDA 외부 이벤트 플래그는 그래프 캡처 중에만 사용한다. 일반 워밍업은 일반 이벤트 기록을 사용한다.
  실제 Orin의 `cudaErrorIllegalState`를 이 구분으로 해결했다.
- GPU 상태 유지의 설치 검사는 같은 모델에 같은 입력 32개와 중간 reset을 적용해
  기존 경로와 주행 출력을 비교한다(`rtol/atol=1e-4`). 두 모드를 별도 프로세스로 순차 실행하여
  첫 TensorRT 엔진의 메모리가 다음 모드까지 남아 생기던 메모리 부족을 피한다.
- AIO의 Python 버퍼 접근 함수 선언을 독립시켜 서명 라이브러리와의 ctypes 선언 충돌을 피한다.

GPU 검사는 상태의 유한값을 유지하지만, 설치 전 비교가 모든 recurrent state의 비트 단위 동일성을
보증하는 것은 아니다. 실패 시 후보를 활성화하지 않고 이전 릴리스를 보존한다.

## 2026-10-16 실측

장치: comma3 + Jetson Orin Nano Super, L4T 36.4.7, TensorRT 10.3.0, 물리 USB SuperSpeed.
공식 기준은 위 `8abfa30c`와 Jetson `989386eb`.
수정본 측정은 콤마 `2396f2b5580edf3bada7abf0034ae797f2500279`,
Jetson `3225eef6bc89d756fdb1b8510a5afc9130cdf0ee`에서 두 성능 옵션을 함께 켠 결과다.
모델은 동일한 RL Nav (80eedcdd), SHA256
`1d18c42ea4cd95c8bffab4635844b78b8e2d4e25b9de44a9c5ac2e0961371a2e`.

차량에서 분리한 탁상에서 실제 카메라·modeld·locationd·운전자 모니터링·plannerd를 실행했다.
워밍업 뒤 60초 일반 입력, 120초 크루즈 활성 입력을 모사했다. 크루즈 구간은 변하는
256×256 합성 지도와 내비게이션 벡터를 정상 모델 입력 경로에 넣었다. 실제 지도 다운로드,
지도 렌더링, 차량 제어, 실제 크루즈 작동을 검증한 결과가 아니다. CAN 출력과 차량 제어 프로세스는 실행하지 않았다.

왕복에서 서버 시간을 뺀 값은 USB 선로 시간만이 아니라 IPC·스케줄링·미계측 구간을 포함한다.
비동기 송신 함수 시간이 줄어도 제출 후 남은 전송은 응답 대기에 잡힐 수 있다.
실제 잔여 평균은 약 0.25ms 증가했다. 이 단일 전후 측정으로 AIO의 이득이나 증가 원인을 확정할 수 없다.
카메라→발행 시간에는 입력 나이와 후처리도 포함되므로 50ms 처리 구간과 구분해야 한다.

두 경우 약 20Hz였고, 모델 생산자 기록에서 생성 프레임 누락/중복은 없었다.
수정본 외부 구독기는 2,401개를 수신했지만 생산자 기록에는 2,402개가 있다.
구독기가 놓친 프레임 3793도 발행 기록과 약 54ms 처리 기록이 있어 위 통계에 포함했다.
수집된 model/odometry/pose 입력·센서·posenet/planner 유효성 오류는 없었다.
수정본 최고 온도는 C3 50.9°C, Jetson 56.031°C였다. 시험 종료 후 설정·보정·CPU 전원 상태와
오프로드 상태를 복원했고 자식 프로세스가 모두 종료됐다.

**평균 개선은 관측됐으나 매 프레임 50ms 또는 실차 안정성을 보장하지 않는다.**
현재 검토용 브랜치는 개인 배포/진단/기본 활성화를 제거한 재구성이므로, 위 결과는 명시한
측정 커밋의 결과다. 이 새 브랜치 자체의 장치 재측정 결과로 바꾸어 해석하면 안 된다.

## 제작자 배포: 암호화 해제가 아니라 공식 서명이 필요

`host.tar.gz`는 암호화되지 않은 소스 패키지다. 별도 복호화 파일이나 개인키를 전달할 필요가 없다.
제작자는 이 소스를 반영한 확정 커밋에서 기존 도구로 패키지를 만들고, 본인의 공식 키로 서명한다.
기존 공식 공개키는 그대로 두며, 이 브랜치에는 개인 USB 공개키/서명 manifest를 넣지 않았다.
기존 공식 ONNX를 계속 쓰므로 모델 파일을 Git에 중복 업로드할 필요도 없다.

공식 NAS 배포 예시(제작자 환경, 실제 모델 URL/키 경로 지정):

```sh
python3 tools/jetlink/build_host_bundle.py /tmp/host.tar.gz
python3 tools/jetlink/sign_release.py \
  --bundle /tmp/host.tar.gz \
  --key /secure/official-ed25519.pem \
  --model-url '<선택된 모델의 공식 HTTPS URL>' \
  --output /tmp/host_release.json
```

`sign_release.py`는 키가 공식 공개키와 일치하는지 검사한다. 생성 manifest의 bundle URL에
같은 패키지를 게시하고, 콤마의 공식 `host_release.json`과 배포 manifest를 제작자의 기존 절차에
맞게 반영해야 한다. 소스를 merge하는 것만으로 기존 Jetson이 새 호스트 코드를 설치하지는 않는다.
성능 옵션도 채택할 경우 패키지 생성 전에 확정 커밋에 포함해야 한다.

선택형 USB 배포는 별도 경로다. 수신 기능과 별도 공개키를 Jetson에 최초 로컬 등록한 뒤,
`prepare_usb_release.py`로 호스트/모델의 해시·크기·URL을 서명한다. 콤마는 오프로드에서만
캐시/전송하고 Jetson은 서명·크기·해시·런타임·모델 계약·설치 전 실행 검사를 통과해야 활성화한다.
공식 NAS 경로는 기존 키/허용 목록을 유지하며, USB 경로가 공식 키를 교체하지 않는다.
USB manifest가 없는 공식 브랜치로 복귀하면 다음 Jetson 정상 부팅에서 공식 선택으로 돌아간다.
공식 파일이 캐시에 없으면 인터넷이 필요하다. 재연결 시 부분 전송 재시작, 완전히 등록된 패키지는 재사용한다.
USB 수신기 최초 등록과 일반 호스트 업데이트는 서로 다른 작업이다.

## 검토 범위 및 검증 한계

주요 파일은 `device_state.py`/`engine.py`/`queues.py`(상태 유지),
`aio_writer_native.py`/`ffs_aio.py`/`daemon.py`(송신),
`usb_release*.py`/`boot_update.py`/`update_host.py`/`startup.py`(업데이트)로 나뉜다.
원 설계 출처와 라이선스는 `third_party/jetlink/UPSTREAM.md`에 남겼다.

기존 실험의 PC 검증과 실제 설치 과정에서 서명 실패·전송 오류·CUDA 이벤트 오류·메모리 부족을
확인하고 수정했다. 설치 검사 성공 후 실제 소스 ID와 GPU 상태 유지 활성화를 확인했다.
성공한 설치 검사의 원시 최대 오차 출력은 수집하지 못했으므로 수치를 주장하지 않는다.
PC의 넓은 171개 검사 중 exported-HUD 검사가 로컬 내보내기/추출 환경 문제로 실패한 이력도 있다.
당시 실제 Orin은 HUD 진입점 import 및 설치 검사를 통과했지만 전체 PC 검사가 통과했다고 표현하지 않는다.

새 자동 테스트 파일은 요청에 따라 배포 브랜치에서 제외했다. 따라서 제작자의 CI에 회귀
검사를 추가하려면 별도 반영이 필요하다. 전원 중단·장시간 운용·실차 크루즈·공식 복귀의 실제
장치 검증과 단독 기능 A/B 비교는 아직 완료하지 않았다.

이 정리본에는 기존 실험의 GPU 상태/AIO/USB 서명·전송/옵션/설치 비교 검사를 임시 적용하여
**83개 통과**를 확인한 뒤 파일을 제거했다. 변경 Python 문법 검사와 diff 공백 검사도 통과했다.
Ruff의 `update_host.py` 영속 상태 시각 기록에 대한 `time.time()` 지적 4개는 공식 기준에도
동일하게 존재한다. 이를 포함한 전체 lint 통과를 주장하지 않는다.

테스트 변경 제외에 따른 알려진 CI 후속 작업: 공식 `test_offline_boot_patch.py`는
**12개 통과, 1개 실패**다. 실패한
`test_installer_enables_once_and_preserves_newer_updater_and_identity`의 `names` 목록에
새 필수 의존 파일 `'usb_release.py'`를 추가해야 한다. 실제 배포 소스에는 그 파일이 있지만
이 검사의 임시 소스 디렉터리에는 없어 `FileNotFoundError`가 발생한다. 기존 실험 브랜치에는
이 준비 목록 수정이 있으나, 이 검토용 브랜치에는 요청에 따라 자동 테스트 변경을 넣지 않았다.
제작자는 통합 전에 해당 준비 목록 및 회귀 검사를 함께 반영해야 한다.

## Jetson USB 화면으로 보내는 HUD의 Wi-Fi 전송

추가 경로는 `콤마 → Wi-Fi → Jetson → USB HUD 화면`이다. ESP32-S3 브리지가
필요한 구성이 아니다. HUD 상태·카메라 미리보기와 내비게이션 미디어를 별도 Wi-Fi
프로세스로 전송하며, 모델 입력과 추론 결과는 기존 USB 경로를 유지한다.
이는 모든 USB 제어 메시지의 제거를 뜻하지 않는다. 연결 협상, 상태 조회,
Wi-Fi 자격 증명 전달과 선택형 업데이트도 기존 USB 경로를 사용한다.

양쪽에 이 코드가 설치되고 Jetson이 `carrot_hud_wifi_v1`을 광고하면 전환한다.
기존 Jetson 또는 다른 호스트에는 기존 USB HUD 경로를 사용한다. 새 경로를 협상한
세션에서는 Wi-Fi 장애가 나도 HUD를 USB에 다시 얹지 않는다. 같은 공유기/핫스팟에서
기기 간 Wi-Fi 통신이 허용돼야 하며, Jetson에 연결된 USB 화면의 렌더러는 유지한다.
이 소스만 콤마에 설치하고 Jetson 호스트 패키지를 업데이트하지 않으면 전환되지 않는다.

- USB 세션 시작 시 임시 256비트 키를 교환한다. 네트워크 키는 argv·상태 파일·로그에
  기록하지 않는다. 세션 종료 시 수신 프로세스와 키를 폐기한다.
- Jetson의 WLAN IPv4에서만 TCP 7716을 수신한다. 콤마도 WLAN 주소에 바인딩하고
  해당 경로를 확인한다. 모델 USB 네트워크 인터페이스를 HUD 우회 경로로 쓰지 않는다.
- 상호 인증 후 AES-GCM으로 전송한다. 스냅샷과 미디어는 별도 연결이며 각각 하나의
  레코드만 응답 대기한다. 크기·순서·인증·400ms 기한을 검사한다.
- 재연결 시 오래된 미디어 대기를 버리고 새 이벤트 경계부터 전달한다. 기존 미디어
  조립기와 키프레임 복구는 유지한다. 스냅샷은 보수적인 수신 지연을 반영하며,
  기존 렌더러의 500ms 만료 판정을 그대로 적용한다.
- 소켓 대기·암호화·재연결은 별도 일반 우선순위 프로세스에서 수행한다. 추론 소유자는
  프레임마다 HUD 파일을 읽거나 Wi-Fi 응답을 기다리지 않는다. 다만 공유 CPU·무선
  자원 사용의 영향까지 없다고 보장하지는 않는다.

양쪽의 `/dev/shm/carrot-jetlink-hud-wifi.json`에는 갱신 시각, 송수신 역할,
스냅샷/미디어 연결 상태와 누적 페이로드 바이트 수만 기록한다. `connected`는 전송
상태이며 물리 화면 표시의 증명은 아니다. Jetson HUD 연결 상태도 함께 확인해야 한다.

PC 검증: 임시 로컬 검사 14개(인증·변조/순서/크기 거부, 전송, 단절/재연결,
USB 중복 차단, 구버전 호환, 프로세스 종료)와 기존 회귀 검사 97개가 통과했다.
후자는 Windows Unicode 경로의 pycapnp 스키마 로딩 문제 때문에 같은 스키마 바이트를
ASCII 임시 경로에서 읽었다. 변경 Python Ruff와 diff 공백 검사도 통과했다.
새 검사 파일은 사용자 요청대로 공개 브랜치에 포함하지 않았다. 실물 Wi-Fi HUD와
추론 지연 비교는 별도 검증 대상이며, 앞 절의 성능 수치를 이 경로의 결과로 해석하면 안 된다.

### 2026-10-16 탁상 장치 측정

콤마3와 Orin에 기존 GPU 상태 유지/AIO 옵션을 동일하게 켠 상태로, USB HUD 기준
`abc33a8d`/호스트 `3225eef6`과 Wi-Fi HUD `5fa4780c`/호스트 `f46e1aa3`를 비교했다.
실제 카메라와 modeld/plannerd를 사용하되, 정상 관리자는 오프로드로 두고 차량 제어
프로세스 없이 정지 상태의 모의 크루즈 입력을 제공했다. 각 시험은 워밍업 후 횡방향
입력 60초와 크루즈 입력 120초이며, 아래 값은 후자의 결과다.

| 측정 항목 | USB HUD | Wi-Fi HUD |
| --- | ---: | ---: |
| 처리 프레임 / 속도 | 2400 / 20.001 Hz | 2401 / 20.000 Hz |
| 전처리 평균 | 4.317 ms | 4.283 ms |
| Jetson 서버 처리 평균 | 25.505 ms | 25.566 ms |
| 클라이언트 왕복에서 서버 처리를 뺀 잔여 평균 | 11.010 ms | 11.775 ms |
| 위 잔여 p99 / 최대 | 21.277 / 34.897 ms | 20.538 / 25.183 ms |
| 전처리를 포함한 모델 실행 평균 / p99 | 41.885 / 52.108 ms | 42.651 / 51.861 ms |
| 모델 실행 50ms 초과 | 29 / 2400 | 44 / 2401 |
| 카메라 프레임 시각부터 결과 발행까지 평균 / p99 | 50.414 / 67.936 ms | 51.259 / 65.659 ms |

두 시험 모두 프레임 ID 누락, 모델·위치 추정·플래너 입력 무효가 관찰되지 않았고,
종료 후 오프로드·전원 상태·변경 파라미터 복원, 보정값 보존, 자식 프로세스 종료를
확인했다. 카메라 대기를 포함한 루프 시간이나 20Hz 평균을 개별 프레임의 50ms 기한
보장으로 해석하면 안 된다. 한 차례씩 순서대로 측정했으므로 재부팅·열·스케줄링
변동이 섞여 있으며, 평균 지연 감소나 일관된 꼬리 지연 개선은 입증되지 않았다.

Wi-Fi 상태 채널의 인증·응답 및 증가하는 전송량을 실제 장치에서 확인했다.
모델용 합성 지도 입력도 처리했지만 HUD 내비게이션 미디어 페이로드는 0바이트였다.
따라서 실시간 지도 영상의 전송·복호화 부하를 검증한 시험은 아니다.
또한 두 시험 모두 `carrot_hud_connected=false`였고 물리 화면은 파란 준비 화면이었다.
`ClusterHudDebug=1` 데이터가 생성되고 새 경로에서는 수신 응답까지 확인됐으나,
Jetson 화면 렌더러의 실제 표시와 시작 실패 원인은 아직 확인하지 못했다.
이 결과를 완성된 HUD 표시 기능이나 실차 크루즈 검증으로 제시하지 않는다.

화면 시작 실패를 확인하기 위해 HUD 시작 단계와 예외 종류·소스 파일명/줄 번호만
`carrot_hud_startup` 상태로 제공한다. 예외 본문·지역 변수·설정·영상은 포함하지 않으며,
서버는 이를 초당 한 번 이하로 읽는다. `renderer_started`도 물리 표시 성공을 뜻하지
않는다. 표시 성공은 기존 `carrot_hud_connected` 출력 갱신으로 따로 확인한다.
진단 정보의 제한과 상태 캐시를 확인하는 로컬 검사 2개가 통과했다.
후속 기존 회귀 검사 97개도 통과했다. 다만 진단 포함 호스트 `c04e0d40`의 실제 USB
설치는 수신 단계에서 거부됐고 상세 원인은 확보하지 못했다. 장치에 설치됐다고
간주하지 않으며, 개인 실험 브랜치의 패키지 선택은 정상 설치됐던 `f46e1aa3`로
되돌렸다. 시작 단계 진단 소스의 실제 장치 검증은 아직 남아 있다.
