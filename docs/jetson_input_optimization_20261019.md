# Jetson 입력 최적화: PC 검증과 적용 판단

기준은 사용자 브랜치의 `85b13334`이다. 실험은 별도 브랜치
`codex/jetson-input-optimization-review`에 분리했다. **새 경로는 기본 꺼짐이며
콤마·Jetson 설치, 서명된 배포 파일, 모델·펌웨어 변경은 하지 않았다.**
아래 성능은 x86 PC의 CPU 입력 준비 측정이다. Orin 추론 속도, 실차 제어,
지속적인 20Hz 또는 매 프레임 50ms 이내 완료를 입증하지 않는다.

## 선택한 후보

`CARROT_TRT_INPUT_FASTPATH=1`을 TensorRT 엔진 생성 전에 명시한 실험에서만:

1. 기존 `np.take`의 범용 인덱스 처리 대신 짧은 C 조회표 함수로 uint8 영상을
   IEEE binary16 비트로 변환한다. 256개 입력 모두 기존 NumPy 변환과 같다.
   함수는 엔진 준비 중 한 번 컴파일·자가 검사하며 프레임 처리 중 컴파일하지 않는다.
2. 이미 협상된 v2 정수 지도 패킷을 중간 float32 배열과 bytes로 재조립하지 않고
   고정 TensorRT 입력 버퍼에 직접 복원한다. 전송 형식과 모델 입력은 유지한다.
3. 고정 버퍼 객체·주소·형식·크기를 확인하고, 바뀌거나 쓰기 불가능하면 실행을 거부한다.

새 옵션은 기존 `runtime_port_options.json`이나 설치 매니페스트에 추가하지 않았다.
ORT/eGPU 엔진은 이 옵션을 읽지 않는다. 기존 GPU 상태 전달 옵션은 독립적이다.
정수 지도 확장이 없는 raw v2/v3 경로에서도 선택 시 영상 변환만 바뀐다.

모든 float 스칼라의 유한성 검사, 모델 출력·전체 recurrent state의 유효성 검사,
초기화와 실패 정책은 유지한다. compact 지도의 픽셀은 형식 자체가 uint8이라
모든 값이 유한하고 0..255이다. 소수·음의 0 등 비정규 지도는 기존 송신기가
압축하지 않으므로 원래 float 경로에서 처리한다. 재전송·오래된 결과 재사용,
추론 순서·대기열·타임아웃·카메라 및 위치 유효성 조건은 바꾸지 않는다.

## 실제 PC 비교

Linux/WSL x86-64, Python 3.10.12, NumPy 2.2.6. 고정 seed의 8개 입력에
빈 지도·ramp·난수 지도와 바뀌는 스칼라를 포함했다. 각 변형은 30회 준비 후
400회 × 5개 묶음을 측정했고 묶음마다 비교 순서를 반대로 했다.
외부 작업을 종료하거나 시스템 스케줄링을 바꾸지 않았다.

| 합성 입력 버퍼 형식 | 기존 평균 / p99 ms | 후보 평균 / p99 ms |
| --- | --- | --- |
| 영상·영상 상태 FP16, 나머지 FP32 | 0.265 / 0.392 | 0.092 / 0.184 |
| 전체 FP16 | 0.357 / 0.550 | 0.101 / 0.190 |
| 전체 FP32 | 0.081 / 0.147 | 0.052 / 0.095 |

이 형식들은 비교용 가정이며 실제 Orin 엔진의 전체 binding 형식이라는 주장이 아니다.
PC 배열은 일반 NumPy 메모리이며 Orin의 CUDA pinned 메모리·캐시 특성을 재현하지 않는다.
FP16 비교의 해당 함수 호출 중 추적된 일시 할당 피크는 3,408,805→2,881 bytes였다.
이는 모델 전체 RAM 사용량이나 GPU 메모리 절감량이 아니다.
일반 OS 스케줄링의 영향이 있으며 FP32 최대 시간은 후보가 더 길었다.

절감량은 약 0.03~0.26ms로 **50ms 전체 예산의 약 0.06~0.52%**이다.
입력 준비의 상대 개선율을 전체 모델 속도 개선율로 해석하면 안 된다.
ARM에서 NumPy의 변환·할당 비용이 다르므로 목표 장치에서 다시 비교해야 한다.

## 추가 후보와 제외 사유

같은 PC 도구로 네이티브 영상 변환 한 작업자와 네 작업자를 비교했다.
평균은 0.071→0.262ms, p99는 0.100→0.398ms로 나빠졌다.
따라서 작은 입력 준비를 CPU 코어 여러 개에 분할하는 변경은 채택하지 않았다.
CPU가 비어 있다는 사실만으로 작업자 수 증가가 이득이라는 근거는 없다.

전체 payload를 새로 복사하는 경우와 고정 버퍼에 복사하는 경우의 평균은
0.00553/0.00567ms였다. 후자는 일시 할당은 줄였지만 속도 개선이 입증되지 않았다.
이 복사만의 비교는 실제 USB 수신 버퍼 풀 구현·소유권·재연결 검증이 아니다.
현재 수신 복사는 다음 읽기가 기존 내용을 덮어쓰지 못하도록 필요하므로 유지했다.

지도 생성의 Jetson CPU 이전은 지도 픽셀만 같아서는 충분하지 않다.
route identity, 원래 위치·지도 나이, 서로 다른 장치 시계와 전송 중 지연까지
검증해야 한다. 현재 공유 지도 렌더러도 이미 별도 낮은 우선순위와 CPU 예산을
사용하므로, 실측 없이 새로운 경로를 추가하지 않았다.

mapped/zero-copy 입력 역시 현재 PC의 외장 GPU 특성을 Orin으로 옮겨 해석할 수 없다.
Tegra의 캐시·일관성·고정 TensorRT binding 주소를 확인한 별도 실험이 필요하다.
[NVIDIA Tegra 메모리 지침](https://docs.nvidia.com/cuda/cuda-for-tegra-appnote/)을
설계 참고로 사용하며, 이 브랜치는 해당 경로를 구현·활성화하지 않는다.

## 파이프라인 모의 실험

`tools/jetlink/simulate_pipeline.py`는 프레임 12,000개씩의 이벤트 모의 실험이다.
입력 주기는 50ms, 대기 슬롯은 단계당 최대 하나이며, 모든 단계 시간은 명시적인
**합성 가정**이다. 실제 TensorRT 실행이나 모델 상태·차량 동역학 시뮬레이터가 아니다.
서로 다른 시계나 카메라 버퍼 수명, 위치·DM 유효성도 입증하지 않는다.

| 가정 | 직렬 / 파이프라인 Hz | 파이프라인 결과 나이 p99 |
| --- | --- | --- |
| GPU 25ms, 입력 준비·전송 12.35ms, 후처리 4ms | 20.00 / 20.00 | 41.35ms |
| 위 조건에 드문 GPU 40ms 추가 지연 | 19.96 / 20.00 | 81.35ms |
| CPU 준비·전송 40ms, GPU 25ms | 14.49 / 20.00 | 69ms |
| GPU 55ms, 나머지는 첫 조건 | 14.01 / 18.18 | 121.35ms |

파이프라인으로 처리율이 높아져도 결과가 더 오래될 수 있다. 직렬 GPU 계산 자체가
50ms를 넘으면 여유 CPU만으로 20Hz를 만들 수 없다. 정상 조건에서는 현재 주기보다
빠른 새 카메라 입력도 없으므로 추가 이득이 없다. 이 결과로 다음 프레임 요청,
동시 추론, 깊은 대기열 또는 결과 재사용을 실제 코드에 도입하지 않았다.

## 회귀 검증과 남은 작업

관련 Linux/Python 3.10 회귀 **411개 통과, 1개 건너뜀**. 건너뜀은 별도 최신
Jetlink 참조 checkout이 없는 선택적 protocol3 통합 검사이며 통과로 세지 않았다.
기존 pytest 설정 경고 3개가 있다. 새 파일 및 변경 파일의 Ruff 검사에는 오류가 없다.

검증에는 모든 uint8 값·배열 끝 경계, 잘못된 자료형·stride·중첩·읽기 전용 메모리,
바인딩 변경, 컴파일 실패, raw v2/v3·compact·LZ4 조합, NaN/무한대 스칼라와
입력 전 실패, 상태 초기화, 바뀌는 입력의 전체 binding 비트·응답 동등성이 포함된다.
deferred CUDA 모의 실행에서는 GPU state 전달·reply 이벤트 순서와 잘못된 출력의
거부·복구를 유지했다. 실제 모델·TensorRT를 실행한 증거로 해석하면 안 된다.

수치 요약은
[`tools/jetlink/validation/input_staging_pc_20261019.json`](../tools/jetlink/validation/input_staging_pc_20261019.json)에 있다.
합성 요약만 포함하며 차량 영상·CAN·위치·키·원시 장치 로그는 포함하지 않는다.

PC 재현 예시(NumPy, pytest, C compiler 필요):

```sh
python3 tools/jetlink/bench_input_staging.py --output /tmp/new-staging-report.json
python3 tools/jetlink/simulate_pipeline.py --output /tmp/new-pipeline-report.json
python3 -m pytest -q -o addopts= --confcutdir=tools/jetlink \
  tools/jetlink/test_direct_inputs.py tools/jetlink/test_staging_tools.py \
  tools/jetlink/test_device_state_port.py
```

Jetson에서의 입력 벤치는 설치된 추론 서비스가 inactive/failed라고 확인할 때만
허용하며 서비스를 자동으로 중지하지 않는다. 실사용 활성화 전에는 같은 엔진·전원·
클록·카메라·경로 조건으로 목표 장치의 개별 A/B/A, 출력과 상태 비트, reset·재연결·
불량 입력, 장시간 부하를 확인해야 한다. 평균뿐 아니라 p99/최대, 50ms 초과 횟수,
촬영부터 발행까지의 나이, 새 프레임 연속성과 DM·pose 상태를 함께 판단해야 한다.
